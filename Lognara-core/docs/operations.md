# Эксплуатация core

Один процесс владеет одним каталогом на локальном SSD. Общая сеть файловых систем и несколько писателей не поддерживаются. `core.lock` запрещает второй процесс. Внешний TLS-прокси принимает HTTPS, core слушает loopback HTTP.

## Конфигурация

Все параметры читаются при запуске. Числа положительные; размер в байтах, если не указано другое. Пустая переменная считается незаданной.

|---|---|---|

| `LOGNARA_QUERY_TOKEN` | обязательна | Другой Bearer для поиска, статистики и `/metrics` |

| `LOGNARA_MAX_BODY_BYTES` | `67108864` | Сжатое тело |

| `RUST_LOG` | `info` | Фильтр tracing |

Ingest budget должен вмещать `body_limit + 2 * (decoded_limit + 1) + model_limit` на запрос; одновременно допускается целое число таких резервов, по умолчанию один. Удвоение учитывает capacity Vec распаковки. До serde выполняется проход MessagePack без аллокаций: 128 байт на узел плюс длины string/bin, проверка фактических размеров контейнеров и глубины. Переполнение модельного бюджета даёт 413. До 64 запросов могут ждать слот не дольше секунды, ещё не читая тело в память приложения; затем 503. Повторы после ожидания получают прежний ACK через дедупликацию.

Это не общий RSS: Arrow, материализатор, индексы, Parquet и запросы требуют дополнительной памяти. Материализация идёт одним потоком; четыре поиска и две аналитики могут выполняться одновременно. Помимо WAL byte-limit действует предел 65536 ожидающих пачек, ограничивающий метаданные для множества маленьких тел. При превышении — 503. Таймаут запросов и refresh ограничены сверху одним часом.

Полные строки поиска читаются с общим бюджетом страницы до разбора JSON attributes: 2048 байт на событие, 8× длины обычных строк и 64× длины JSON attributes. Консервативные коэффициенты учитывают дерево Value, capacity контейнеров и сериализацию ответа. При превышении — 503 без частичной страницы; уменьшите `limit` или увеличьте `LOGNARA_SEARCH_MEMORY_BYTES`. Читатель Parquet выдаёт выбранные строки по одной, хотя декодирование физической страницы может временно требовать дополнительную память.

Токены задавайте в закрытом environment-файле сервиса. Admin-токен нужен core и dock; relay хранит только свой персональный токен, агенты — свои. Реестр `access.sqlite3` с хешами входит в резервную копию всего каталога данных. Relay и агенты регистрируются через dock/admin API; их токены выдаются один раз. При пересоздании профиля обновите токен соответствующего процесса: 401/403 сохраняют пачки в spool. Все три лимита relay `LOGNARA_CORE_MAX_BODY_BYTES`, `LOGNARA_CORE_MAX_DECODED_BYTES`, `LOGNARA_CORE_MAX_MODEL_BYTES` должны соответствовать core. Не уменьшайте их, пока старые крупные пачки ожидают в spool: core возвращает окончательный 413. Одиночное событие, превышающее лимиты, relay диагностирует и учитывает как потерю; разделить его без изменения контракта невозможно.

## Мониторинг инфраструктуры

Query-защищённый `GET /v1/status` возвращает version/ready, visible sequence и lag публикации, WAL used/limit, текущие Parquet/index bytes (индекс включает активный сегмент), число закрытых сегментов, oldest event, настроенный retention и total/available filesystem data_dir. Это не квота Lognara и не p95 доставки. Размеры могут меняться при работе активного индекса.

`POST /v1/heartbeat` с персональным relay-токеном сохраняет последний отчёт relay/его агентов в access.sqlite3. Agent/relay используют `LOGNARA_HEARTBEAT_INTERVAL_MS` default 10000 (1..30000 мс); admin-списки включают heartbeat/as_of. Dock `/infrastructure` использует TTL 60 с, idle 300 с, spool 80%, явно отличает unknown и устаревшие данные. История измерений/прогноз не ведутся. [Полный контракт](../../docs/DockInfrastructureContract.md).

## Запуск за HTTPS

Из корня репозитория:

```sh
cargo build --release --locked --manifest-path Lognara-core/Cargo.toml --bin lognara-core
```

Установите бинарник в `/usr/local/bin/lognara-core`, создайте отдельного пользователя сервиса и каталог данных с правом записи. Пример Linux systemd (пути адаптировать к серверу):

```ini
[Unit]
Description=Lognara Core
After=network.target

[Service]
User=lognara
Group=lognara
EnvironmentFile=/etc/lognara-core.env
ExecStart=/usr/local/bin/lognara-core
Restart=on-failure
TimeoutStopSec=120
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

Пример блока nginx внутри `http {}`; сертификаты и домен заменяются на фактические:

```nginx
server {
    listen 443 ssl;
    server_name logs.example.com;
    ssl_certificate /etc/letsencrypt/live/logs.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/logs.example.com/privkey.pem;
    client_max_body_size 64m;
    client_body_timeout 30s;

    location / {
        proxy_pass http://127.0.0.1:7402;
        proxy_http_version 1.1;
        proxy_request_buffering off;
        proxy_read_timeout 40s;
        proxy_send_timeout 40s;
    }
}
```

Прокси должен передавать Authorization, Content-Type, Content-Encoding и исходное тело без распаковки или перекодирования. Лимит прокси не ниже лимита core. Настройку nginx проверьте `nginx -t` на целевом сервере; пример не устанавливает прокси и сертификаты автоматически.

## Долговечность и восстановление

Гарантия core начинается с 204. Потерянный ответ безопасно повторяется теми же байтами. Дедупликация всей пачки действует минимум семь суток и пока сохраняются её данные. Перегруппированные события считаются новой пачкой.

WAL: одна запись на файл, версия, длина, CRC32, SHA-256, номера и время приёма. Временный файл синхронизируется, переименовывается, каталог синхронизируется до ACK. При старте незавершённые `.tmp` удаляются; повреждённый опубликованный WAL останавливает запуск с ошибкой. Core восстанавливает очередь до начала HTTP-обслуживания, поэтому во время восстановления readiness ещё недоступен.

Сегмент: `segments/YYYY/MM/DD/<id>/{logs.parquet,index/,meta.json}`. Дата пути — время core; отбор поиска — фактический диапазон времени событий. SQLite в WAL/FULL режиме атомарно сохраняет сегмент, позицию внутри пачки и receipts перед освобождением WAL. Незарегистрированные каталоги пересоздаются из WAL. Отсутствующий или повреждённый индекс перестраивается из Parquet; запрос может получить 503/504, но не частичный результат.

Точки метрик: `metrics/YYYY/MM/DD/<id>.parquet`, один файл на закрытый сегмент, в котором есть точки; дата - время core. Parquet пишется через `.tmp`, синхронизируется и переименовывается до SQLite-транзакции сегмента. Эта транзакция регистрирует файл в `series_files` (состояние `ready`), имена серий в `series_names`, а вместе с ними сегмент, receipts и позицию внутри пачки. При старте `.parquet` и `.tmp` в каталогах дней, которых нет в `ready`, удаляются; зарегистрированный файл, отсутствующий на диске, останавливает запуск. Retention файлы метрик не удаляет.

Слияние: когда все файлы дня старше `LOGNARA_SERIES_COMPACT_QUIET_SECONDS`, материализатор за проход сливает один день (от двух файлов) в новый файл. Одна транзакция переводит новый файл в `ready`, исходные в `deleting`. Исходные файлы удаляются после завершения читающих их запросов; незавершённое удаление продолжается при старте. Счётчик слияний: `lognara_core_series_compactions_total`.

Агрегаты: сутки UTC, закончившиеся позже `LOGNARA_SERIES_RAW_DAYS` назад, агрегатов не получают. Сутки старше этого срока, но не старше `LOGNARA_SERIES_HOURLY_DAYS`, получают `rollups/1h/YYYY/MM/DD/<id>.parquet` (корзины по часу), а более старые сутки - `rollups/12h/...` (корзины 00:00 и 12:00 UTC). Строят их в фоне, поток `lognara-rollups`, по одним суткам за проход; сырые точки остаются источником истины. Сутки перестраиваются, если изменился отпечаток их файлов серий, то есть пришёл поздний файл или прошло слияние. Старый файл удаляется, когда его больше не читают. При старте файлы без строки в `series_rollups` удаляются, строка без файла пересобирается. Ошибки построения только считаются (`lognara_core_series_rollup_errors_total`) и не останавливают core; построенные сутки считаются в `lognara_core_series_rollups_built_total`. Запрос `POST /v1/series/query` берёт агрегат вместо точек, если сутки целиком внутри окна, корзина делит `step_seconds`, отпечаток совпадает с текущими файлами и в открытом сегменте нет точек этих суток; остальное читается сырыми точками. Значения совпадают с сырыми с точностью до порядка сложения вещественных чисел.

SIGTERM/SIGINT прекращает HTTP, дожидается принятых запросов, материализует WAL и закрывает сегмент. Если процесс завершён принудительно, подтверждённые данные восстанавливаются из WAL. Для согласованной резервной копии остановите core и скопируйте **весь** каталог данных; отдельный Parquet не сохраняет receipts/checkpoint. Ручное удаление WAL или правка SQLite не являются восстановлением.

Retention удаляет только закрытый сегмент, в котором последнее событие поступило раньше срока. Сначала ставится `deleting`, сегмент исключается из новых снимков, затем завершаются текущие чтения и удаляются файлы. Просроченный открытый сегмент дождётся закрытия. После рестарта незавершённое удаление продолжается. Курсоры после рестарта или retention возвращают 410.

При нехватке места core возвращает 503; подтверждённые данные досрочно не удаляет. Добавьте место или дождитесь штатного retention. Ошибка записи WAL/материализации снимает readiness до устранения причины и рестарта.

## Наблюдение

`/health/live` — процесс отвечает; `/health/ready` — завершено восстановление, writer исправен и остановка не начата. Health без токена. `/metrics` требует query-токен, формат Prometheus.

Счётчики `lognara_core_*`: принятые пачки/события, повторы, отказы writer, потери relay/агентов, закрытые/удалённые сегменты, запросы/ошибки, суммарное время ACK и запросов. Gauges: байты WAL, опубликованный sequence, возраст самой старой ещё не опубликованной пачки на момент обновления снимка. Счётчики сбрасываются при рестарте; временные суммы не дают p99 — для него используйте стенд или метрики клиента. Содержимое логов и токены в labels не попадают.

Счётчики точек метрик: `lognara_core_series_points_total` (сохранённые точки), `lognara_core_series_parse_errors_total` (отчёты или значения с ошибкой разбора; сообщение при этом остаётся логом), `lognara_core_series_dropped_points_total` (точки правил, отброшенные лимитом 1000 различных наборов меток на правило; набор ведётся в памяти и после рестарта начинается заново), `lognara_core_series_compactions_total` (слияния дней).

Следите за ростом WAL, свободным диском, RSS и ошибками запросов. При 10000 событий/с за семь суток приходит 6,048 млрд событий; SSD рассчитывается по измеренному Parquet + индексу, с резервом на WAL, открытый сегмент, слияния индекса и восстановление.

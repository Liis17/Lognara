# Lognara

Lognara содержит отдельные Rust-crates agent, relay, core и общий spool. Агент принимает HTTP, файлы и stdout/stderr; relay нормализует события, core хранит и ищет логи. Актуальные контракты описаны в Obsidian и подтверждаются исходниками.

### Чтение памяти

- Перед работой прочитай `Index.md` и относящиеся к задаче заметки. При обычном обновлении изучай затронутые исходники; полный обзор нужен при общих архитектурных изменениях или явном запросе на полную актуализацию.
- Проверяй сведения по актуальному коду, конфигурации и документации. Память не заменяет проверку исходников.
- Для работы с памятью используй доступные средства поиска и работы с файлами; при наличии `rg` предпочитай его. Навык не требует конкретного инструмента, субагента или модели.

### Обновление памяти

- Храни назначение и границы компонентов, значимые публичные контракты, зависимости, взаимодействия, ключевые потоки, ограничения и подтверждённые причины решений. Указывай реальные пути исходников и важные символы.
- Описывай контракты по смыслу; не копируй код, полные списки методов и полей и очевидные детали реализации. Внутренние вспомогательные функции, косметические изменения и рефакторинг без изменения поведения или архитектуры не требуют обновления памяти.
- Обновляй описанное поведение на месте при изменении контракта, потока, зависимости или ограничения. Удалённые контракты и неверные сведения убирай без зачёркиваний и датированных записей.
- Перед созданием заметки ищи существующую по назначению, названию и исходникам. Дополняй её, сохраняя полезные сведения и ручные дополнения. Описание контракта или основания решения храни в одном месте, из остальных заметок ссылайся на него.
- Значимые компоненты размещай в папках фактических доменов. Добавляй новую значимую заметку в навигацию `Index.md`; каждая такая заметка должна быть достижима из индекса напрямую или через связанные заметки.

- Устройство компонента подтверждай реализацией. Причины выбора подтверждай документацией, объясняющими комментариями или словами пользователя; неизвестные важные причины отмечай как не задокументированные. `Decisions.md` создавай только при необходимости отдельного подробного объяснения нескольких решений.

## Проверка затронутых компонентов

- Для изменений agent, relay, core, dock и общего spool определяй зависимые места вызова, HTTP-клиенты, фоновые задачи и конфигурацию Docker Compose. Каждый Rust-crate собирается отдельно; общего Cargo workspace нет.
- При изменении MessagePack + zstd между agent → relay → core, HTTP/JSON API, SSE, форматов spool/WAL/Parquet, схем SQLite или конфигурации `LOGNARA_*` проверяй производителей и потребителей. Учитывай совместимость wire-фикстур в тестах relay и core.
- Учитывай React/TypeScript-клиент в `Lognara-dock/web/`, Rust-прокси dock и CLI агента там, где изменение их затрагивает.
- Сохраняй совместимость публичных контрактов и сохранённых данных без явной необходимости её менять. При добавлении создания, включения или подключения проверяй необходимость удаления, отключения и восстановления.
- Меняй только затронутые компоненты и явно указывай, что не проверено.

## Архитектурные границы

- HTTP-обработчики axum в agent, relay, core и dock принимают и проверяют запрос, вызывают соответствующий сервис или модуль и формируют ответ. Не добавляй в транспортный слой самостоятельную бизнес-логику.
- Сохраняй разделение стадий конвейера: сбор в agent, нормализация в relay, хранение и запросы в core, сессии и проксирование в dock.
- Перед созданием общей абстракции проверяй `Lognara-spool/`; не переноси туда логику только ради одного потребителя.
- Не изменяй публичные контракты без проверки обратной совместимости у зависимых компонентов.

## HTTP и durable-доставка

- Сохраняй подтверждение agent/relay только после durable-записи всей принятой группы в spool, а core — после fsync WAL. Не удаляй очередь до успешного ACK следующего сервиса.
- Учитывай повторы при сбоях и восстановлении: подготовленные пачки повторяются теми же байтами, core дедуплицирует тело по SHA-256; повтор исходного запроса может создать новые ID событий.
- Сохраняй квоты диска, ограничения тела и распаковки, резервы памяти и поведение при перегрузке. Не добавляй блокирующие операции в горячий асинхронный путь tokio; используй существующие blocking-работники.
- Учитывай отмену, таймауты и ошибки HTTP-вызовов, включая завершение фоновых операций при остановке.
- Сохраняй проверку персонального токена агента в relay до чтения тела и распаковки. Не меняй разделение relay/admin/query-токенов без обоснования; query/admin-токены core должны оставаться в dock и не попадать в браузер.

## Проверка изменений

- Проверяй минимальный достаточный набор: изменённый компонент, затронутые тесты и зависимые контракты. Не запускай полную сборку всех crate без необходимости; для сквозных изменений расширяй проверку.
- Для затронутых Rust-crate используй проверки из `.github/workflows/ci.yml`: `cargo fmt --all --check`, `cargo clippy --locked --all-targets --all-features -- -D warnings`, `cargo build --locked`, `cargo test --locked --all-features`. Запускай их из каталога crate; у core `--all-features` включает `crash-tests`.
- При изменении памяти agent/relay проверяй соответствующий `tests/check-memory-profile.py`. Для веб-клиента используй `npm run build`, `npm test` и относящиеся к изменению Playwright-сценарии через `npm run test:e2e` из `Lognara-dock/web/`.
- Для исправления бага по возможности добавляй воспроизводящий тест; для новой значимой логики — проверки ожидаемого поведения и существенных ошибок. Не создавай тесты, лишь повторяющие реализацию или очевидную передачу параметров.
- В асинхронных тестах предпочитай ожидание наблюдаемого события или состояния произвольным задержкам.
- Не сообщай, что тесты прошли, если они не запускались. Если проверка невозможна, указывай конкретную причину.

## Безопасность окружения

- Не запускай миграции и не изменяй рабочие SQLite-базы core/dock без явного разрешения.
- Не выполняй `docker compose down -v`, удаление volumes, spool, WAL, сегментов или пользовательских данных без разрешения.
- Не останавливай процессы по шаблону имени через `pkill -f` или аналогичные команды; останавливай только процессы, принадлежность которых текущей задаче подтверждена.
- Не изменяй секреты, токены, реальные конфигурации и переменные окружения (`.env`, `Example/.env`, htpasswd, `LOGNARA_*`) без необходимости и разрешения.
- Для тестов используй отдельное окружение и изолированные данные. Не коммить временные файлы агента, диагностические дампы, логи и исследовательские заметки.

## Производительность

- Для изменений в горячем пути оцени влияние на задержки, память, CPU и количество сетевых обращений.
- Избегай лишних запросов к SQLite, повторной сериализации и ненужных аллокаций; учитывай стоимость поиска Tantivy и аналитики DataFusion/Parquet.
- Не передавай крупные объекты по HTTP/SSE без необходимости и не блокируй асинхронный код синхронным ожиданием.
- В React избегай ненужных перерисовок, постоянных анимаций и полной переработки списков при небольших изменениях.
- Не оптимизируй без доказанной причины: сначала установи проблему, затем устраняй её.

## Создание Pull Request

### Когда создавать PR

- Создавай Pull Request на GitHub только по явному запросу пользователя. Такой запрос разрешает необходимую отдельную ветку и push, если пользователь отдельно не запретил эти действия.
- Если пользователь просит только подготовить PR, не выполняй push и создание PR автоматически.
- Один PR должен решать одну логически связанную задачу; не объединяй несвязанные исправления, рефакторинг и новые функции. Не создавай дубликат уже открытого PR для этой задачи.

### Ветки и коммиты

- Целевая ветка по умолчанию — `master` (`origin/HEAD`). Другие долгоживущие ветки и схема продвижения изменений не подтверждены; не придумывай их. Учитывай явно указанную пользователем целевую ветку.
- Для PR используй отдельную рабочую ветку от актуальной целевой, сохраняя принятую схему `t3/<short-description>`. Если задача уже выполняется в отдельной ветке, используй её. Не изменяй `master` напрямую ради создания PR.
- Не включай в PR чужие незакоммиченные изменения. Соблюдай русский язык и ограничения сообщений коммитов из раздела Git; Conventional Commits и обязательные scope в проекте не установлены.
- Название PR пиши по-русски, кратко описывая конкретный результат. Примеры: `Исправить повторную доставку пачек relay`, `Добавить фильтр окружения в графики Dock`, `Обновить правила памяти проекта`.

### Перед созданием PR

1. Проверь полный diff относительно целевой ветки: все файлы относятся к задаче, нет случайного форматирования и несвязанных правок.
2. Проверь корректность и совместимость изменений, запусти доступные целевые тесты и сборки по инженерным правилам.
3. Убедись, что необходимые изменения памяти в `Obsidian/LognaraVault/` внесены.
4. Проверь отсутствие секретов, токенов и временных файлов.

Не запускай автоматически всю сборку монорепозитория: проверяй затронутые crate и веб-клиент, расширяя объём при необходимости.

### Описание PR

Шаблон PR в репозитории не обнаружен. Используй следующую структуру, пропуская пустые и неприменимые разделы:

**Summary**

- Что изменено, какую проблему решает и какие технические решения нужны для понимания изменения.

**Testing**

- Какие тесты, проверки и сборки выполнены, их результаты; что не проверено и почему.

**Compatibility & Risks**

- Какие части agent, relay, spool, core, dock и веб-клиента затронуты.
- Изменения MessagePack/HTTP/JSON/SSE-контрактов, форматов сохранённых данных, SQLite или конфигурации.
- Ограничения, риски и необходимые действия при развёртывании.

**Visual Changes** (для UI)

- Скриншоты до и после, если доступны; для существенных изменений анимаций — короткая видеодемонстрация, если возможно.

### После создания PR

- Убедись, что PR направлен в правильную ветку.
- Проверь GitHub Actions в `.github/workflows/ci.yml`, включая итоговую проверку `CI passed`; не утверждай, что CI прошёл, до подтверждения GitHub. Публикация образов запускается после успешного CI только при push в `master` и не является проверкой PR.
- Если пользователь попросил сопровождать PR, следи за новыми результатами CI и комментариями после последнего изменения.
- Проверяй замечания автоматических ревьюеров по исходникам. Исправляй подтверждённые проблемы, для ложных срабатываний указывай техническую причину.
- Не выполняй merge без явного разрешения пользователя.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.

# Lognara

Lognara содержит отдельные Rust-crates agent, relay, core и общий spool. Агент принимает HTTP, файлы и stdout/stderr; relay нормализует события, core хранит и ищет логи. Актуальные контракты описаны в Obsidian и подтверждаются исходниками.

### Чтение памяти

- Перед работой прочитай `Index.md` и относящиеся к задаче заметки. При обычном обновлении изучай затронутые исходники; полный обзор нужен при общих архитектурных изменениях или явном запросе на полную актуализацию.
- Проверяй сведения по актуальному коду, конфигурации и документации. Память не заменяет проверку исходников.
- Для работы с памятью используй доступные средства поиска и работы с файлами; при наличии `rg` предпочитай его. Навык не требует конкретного инструмента, субагента или модели.

### Обновление памяти

- Храни назначение и границы компонентов, значимые публичные контракты, зависимости, взаимодействия, ключевые потоки, ограничения и подтверждённые причины решений. Указывай реальные пути исходников и важные символы.
- Описывай контракты по смыслу; не копируй код, полные списки методов и полей и очевидные детали реализации. Внутренние вспомогательные функции, косметические изменения и рефакторинг без изменения поведения или архитектуры не требуют обновления памяти.
- Обновляй описанное поведение на месте при изменении контракта, потока, зависимости или ограничения. Удалённые контракты и неверные сведения убирай без зачёркиваний и датированных записей.
- Перед созданием заметки ищи существующую по назначению, названию и исходникам. Дополняй её, сохраняя полезные сведения и ручные дополнения. Описание контракта или основания решения храни в одном месте, из остальных заметок ссылайся на него.
- Значимые компоненты размещай в папках фактических доменов. Добавляй новую значимую заметку в навигацию `Index.md`; каждая такая заметка должна быть достижима из индекса напрямую или через связанные заметки.

- Устройство компонента подтверждай реализацией. Причины выбора подтверждай документацией, объясняющими комментариями или словами пользователя; неизвестные важные причины отмечай как не задокументированные. `Decisions.md` создавай только при необходимости отдельного подробного объяснения нескольких решений.

## Проверка затронутых компонентов

- Для изменений agent, relay, core, dock и общего spool определяй зависимые места вызова, HTTP-клиенты, фоновые задачи и конфигурацию Docker Compose. Каждый Rust-crate собирается отдельно; общего Cargo workspace нет.
- При изменении MessagePack + zstd между agent → relay → core, HTTP/JSON API, SSE, форматов spool/WAL/Parquet, схем SQLite или конфигурации `LOGNARA_*` проверяй производителей и потребителей. Учитывай совместимость wire-фикстур в тестах relay и core.
- Учитывай React/TypeScript-клиент в `Lognara-dock/web/`, Rust-прокси dock и CLI агента там, где изменение их затрагивает.
- Сохраняй совместимость публичных контрактов и сохранённых данных без явной необходимости её менять. При добавлении создания, включения или подключения проверяй необходимость удаления, отключения и восстановления.
- Меняй только затронутые компоненты и явно указывай, что не проверено.

## Архитектурные границы

- HTTP-обработчики axum в agent, relay, core и dock принимают и проверяют запрос, вызывают соответствующий сервис или модуль и формируют ответ. Не добавляй в транспортный слой самостоятельную бизнес-логику.
- Сохраняй разделение стадий конвейера: сбор в agent, нормализация в relay, хранение и запросы в core, сессии и проксирование в dock.
- Перед созданием общей абстракции проверяй `Lognara-spool/`; не переноси туда логику только ради одного потребителя.
- Не изменяй публичные контракты без проверки обратной совместимости у зависимых компонентов.

## HTTP и durable-доставка

- Сохраняй подтверждение agent/relay только после durable-записи всей принятой группы в spool, а core — после fsync WAL. Не удаляй очередь до успешного ACK следующего сервиса.
- Учитывай повторы при сбоях и восстановлении: подготовленные пачки повторяются теми же байтами, core дедуплицирует тело по SHA-256; повтор исходного запроса может создать новые ID событий.
- Сохраняй квоты диска, ограничения тела и распаковки, резервы памяти и поведение при перегрузке. Не добавляй блокирующие операции в горячий асинхронный путь tokio; используй существующие blocking-работники.
- Учитывай отмену, таймауты и ошибки HTTP-вызовов, включая завершение фоновых операций при остановке.
- Сохраняй проверку персонального токена агента в relay до чтения тела и распаковки. Не меняй разделение relay/admin/query-токенов без обоснования; query/admin-токены core должны оставаться в dock и не попадать в браузер.

## Проверка изменений

- Проверяй минимальный достаточный набор: изменённый компонент, затронутые тесты и зависимые контракты. Не запускай полную сборку всех crate без необходимости; для сквозных изменений расширяй проверку.
- Для затронутых Rust-crate используй проверки из `.github/workflows/ci.yml`: `cargo fmt --all --check`, `cargo clippy --locked --all-targets --all-features -- -D warnings`, `cargo build --locked`, `cargo test --locked --all-features`. Запускай их из каталога crate; у core `--all-features` включает `crash-tests`.
- При изменении памяти agent/relay проверяй соответствующий `tests/check-memory-profile.py`. Для веб-клиента используй `npm run build`, `npm test` и относящиеся к изменению Playwright-сценарии через `npm run test:e2e` из `Lognara-dock/web/`.
- Для исправления бага по возможности добавляй воспроизводящий тест; для новой значимой логики — проверки ожидаемого поведения и существенных ошибок. Не создавай тесты, лишь повторяющие реализацию или очевидную передачу параметров.
- В асинхронных тестах предпочитай ожидание наблюдаемого события или состояния произвольным задержкам.
- Не сообщай, что тесты прошли, если они не запускались. Если проверка невозможна, указывай конкретную причину.

## Безопасность окружения

- Не запускай миграции и не изменяй рабочие SQLite-базы core/dock без явного разрешения.
- Не выполняй `docker compose down -v`, удаление volumes, spool, WAL, сегментов или пользовательских данных без разрешения.
- Не останавливай процессы по шаблону имени через `pkill -f` или аналогичные команды; останавливай только процессы, принадлежность которых текущей задаче подтверждена.
- Не изменяй секреты, токены, реальные конфигурации и переменные окружения (`.env`, `Example/.env`, htpasswd, `LOGNARA_*`) без необходимости и разрешения.
- Для тестов используй отдельное окружение и изолированные данные. Не коммить временные файлы агента, диагностические дампы, логи и исследовательские заметки.

## Производительность

- Для изменений в горячем пути оцени влияние на задержки, память, CPU и количество сетевых обращений.
- Избегай лишних запросов к SQLite, повторной сериализации и ненужных аллокаций; учитывай стоимость поиска Tantivy и аналитики DataFusion/Parquet.
- Не передавай крупные объекты по HTTP/SSE без необходимости и не блокируй асинхронный код синхронным ожиданием.
- В React избегай ненужных перерисовок, постоянных анимаций и полной переработки списков при небольших изменениях.
- Не оптимизируй без доказанной причины: сначала установи проблему, затем устраняй её.

## Создание Pull Request

### Когда создавать PR

- Создавай Pull Request на GitHub только по явному запросу пользователя. Такой запрос разрешает необходимую отдельную ветку и push, если пользователь отдельно не запретил эти действия.
- Если пользователь просит только подготовить PR, не выполняй push и создание PR автоматически.
- Один PR должен решать одну логически связанную задачу; не объединяй несвязанные исправления, рефакторинг и новые функции. Не создавай дубликат уже открытого PR для этой задачи.

### Ветки и коммиты

- Целевая ветка по умолчанию — `master` (`origin/HEAD`). Другие долгоживущие ветки и схема продвижения изменений не подтверждены; не придумывай их. Учитывай явно указанную пользователем целевую ветку.
- Для PR используй отдельную рабочую ветку от актуальной целевой, сохраняя принятую схему `t3/<short-description>`. Если задача уже выполняется в отдельной ветке, используй её. Не изменяй `master` напрямую ради создания PR.
- Не включай в PR чужие незакоммиченные изменения. Соблюдай русский язык и ограничения сообщений коммитов из раздела Git; Conventional Commits и обязательные scope в проекте не установлены.
- Название PR пиши по-русски, кратко описывая конкретный результат. Примеры: `Исправить повторную доставку пачек relay`, `Добавить фильтр окружения в графики Dock`, `Обновить правила памяти проекта`.

### Перед созданием PR

1. Проверь полный diff относительно целевой ветки: все файлы относятся к задаче, нет случайного форматирования и несвязанных правок.
2. Проверь корректность и совместимость изменений, запусти доступные целевые тесты и сборки по инженерным правилам.
3. Убедись, что необходимые изменения памяти в `Obsidian/LognaraVault/` внесены.
4. Проверь отсутствие секретов, токенов и временных файлов.

Не запускай автоматически всю сборку монорепозитория: проверяй затронутые crate и веб-клиент, расширяя объём при необходимости.

### Описание PR

Шаблон PR в репозитории не обнаружен. Используй следующую структуру, пропуская пустые и неприменимые разделы:

**Summary**

- Что изменено, какую проблему решает и какие технические решения нужны для понимания изменения.

**Testing**

- Какие тесты, проверки и сборки выполнены, их результаты; что не проверено и почему.

**Compatibility & Risks**

- Какие части agent, relay, spool, core, dock и веб-клиента затронуты.
- Изменения MessagePack/HTTP/JSON/SSE-контрактов, форматов сохранённых данных, SQLite или конфигурации.
- Ограничения, риски и необходимые действия при развёртывании.

**Visual Changes** (для UI)

- Скриншоты до и после, если доступны; для существенных изменений анимаций — короткая видеодемонстрация, если возможно.

### После создания PR

- Убедись, что PR направлен в правильную ветку.
- Проверь GitHub Actions в `.github/workflows/ci.yml`, включая итоговую проверку `CI passed`; не утверждай, что CI прошёл, до подтверждения GitHub. Публикация образов запускается после успешного CI только при push в `master` и не является проверкой PR.
- Если пользователь попросил сопровождать PR, следи за новыми результатами CI и комментариями после последнего изменения.
- Проверяй замечания автоматических ревьюеров по исходникам. Исправляй подтверждённые проблемы, для ложных срабатываний указывай техническую причину.
- Не выполняй merge без явного разрешения пользователя.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.

## Оркестрация субагентов (T3 Code)

Блок установлен навыком `agents-md-orchestration`; он самодостаточен и работает
без установленного навыка. При явном запросе обновления навык заменяет только
содержимое между этими маркерами. Единственное определение моделей и уровней —
таблица ролей в «Разрешённых маршрутах и ролях»; новые стабильные версии тех же
семейств подходят без правки правил, если есть в T3 и поддерживают нужный effort.

### Исходный режим сессии

Правила действуют только внутри T3 Code с подтверждённым
`orchestrator_capabilities`. Определи исходный режим по сведениям запуска
или истории и сохраняй его при сжатии контекста. Текущий `interactionMode`
сам по себе не доказывает исходный режим. Если его нельзя установить
и это влияет на процесс, уточни у пользователя.

- **Начальный Plan Mode:** основной агент читает код, уточняет существенные
  требования и составляет план. Обязательны независимое ревью плана другим
  провайдером, разрешение замечаний и подтверждение финального плана
  пользователем. До подтверждения реализации нет; после него основной
  агент не пишет и не исправляет код, включая тесты, интеграцию и конфликты.
- **Начальный обычный режим:** основной агент может сам изучать задачу,
  писать код и проверять результат. Делегирование необязательно; полная
  цепочка Plan Mode и обязательное подтверждение плана не навязываются.
  При делегировании код и тесты получает один исполнитель по таблице ролей.

Переключение режима не меняет исходный процесс; явное указание пользователя
может изменить согласованный порядок. Правила проверки diff, рисков,
контекста и повторов ниже действуют в обоих режимах.

### Разрешённые маршруты и роли

Разрешены только OpenAI через официальный Codex и Anthropic через официальный
Claude Code. Проверяй провайдера и harness по каталогу T3, а не отображаемому
имени. OpenRouter и OpenCode запрещены для всех ролей, включая запасные маршруты.

Каждая строка задаёт семейство, минимальную версию и обязательный effort;
выбирай новейшую доступную стабильную подходящую версию, а не фиксированный
релиз. Знак `+` задаёт нижнюю границу семейства, а не закрепляет релиз.

| Роль | Семейство и минимум | Effort |
| --- | --- | --- |
| Ревью плана при основном агенте Anthropic | Sol 6.1+ (OpenAI/Codex) | medium |
| Ревью плана при основном агенте OpenAI | Opus 5.5+ (Anthropic/Claude Code) | medium |
| Исполнитель по умолчанию: код, проверки, исправления | Luna 5+ (OpenAI/Codex) | max |
| Альтернативный исполнитель | Haiku 5.5+ (Anthropic/Claude Code) | high |
| Независимое ревью большого и сложного кода или по риску | Sonnet 5+ (Anthropic/Claude Code) | high |
| Необязательный эксперт сложной диагностики | Sol 6.1+ / Opus 5.5+, по возможности другой провайдер | medium |

Luna max — сознательное предпочтение пользователя, не снижать effort ради
экономии. Haiku допустим при Claude-приоритете пользователя, недоступности
Luna, большей пригодности для задачи или распределении расхода между квотами.
Не запускай обоих для одного задания «на всякий случай». Без подтверждённых
данных о квотах выбирай Luna; не утверждай, что T3 показывает остатки лимитов.

### Динамический выбор и кеш возможностей

В начале активной рабочей сессии вызови `orchestrator_capabilities` один раз
и сохрани проверенные providerInstanceId, model ID, опции и ограничения.
Если каталог сокращён (`omittedModels`), используй поиск по нужным семействам
для завершения начального подбора; короткая выдача не доказывает отсутствие
более новой модели. Повторно используй результаты вместо вызова на каждого
агента. Обновляй при смене провайдера/конфигурации, ошибке доступности,
явно устаревшем состоянии, запросе свежих моделей или после значительного
простоя до делегирования.

Правила подбора:

1. Сверяй устойчивое семейство и версию из метаданных каталога; если отдельных
   полей нет, используй однозначную структуру официального model ID из каталога.
   Совпадения подстроки в display name недостаточно. Не выдумывай поля или ID;
   неоднозначную принадлежность/версию считай неподтверждённой.
2. Сравнивай версии численно по компонентам (недостающие компоненты — нули):
   6.10 > 6.5. Новая major-версия того же семейства также допустима.
   Preview/nightly/beta и другие предварительные релизы исключены без
   разрешения пользователя; не выдавай неподтверждённый статус за стабильный.
3. Фильтруй по официальному harness, минимуму версии, доступности дочерних
   задач и реальной поддержке требуемого effort, затем выбирай новейший вариант.
   Проверяй имена опций и значения: обычно Codex — `reasoningEffort`,
   Claude — `effort`. Не подменяй max/high/medium другим уровнем.
4. Если подходящей модели/уровня нет, используй лишь альтернативу той же роли,
   уже разрешённую таблицей; иначе сообщи пользователю ограничение и дождись
   решения для зависимого шага. Не обходи обязательное ревью, не выдумывай ID
   и не используй другого провайдера или семейство без согласования.
5. Передавай реальные `providerInstanceId`, `model` и настройки в
   `target.options` для T3 `delegate_task`, а не только текстом в задании.
   Проверяй возвращённые провайдер, модель и опции. Несовпадение —
   ограничение возможности, не успех.

Поскольку роли задают явный effort, используй T3 `delegate_task`: нативные
субагенты ненадёжно передают T3 model options. Учитывай `inheritedOptions`
только для того же провайдера и модели, явно переопределяя effort роли;
не включай fastMode или другие платные настройки без оснований.
Создавай дочерние задачи, а не отдельные беседы через `t3_thread_launch`
или `create_threads`.

### Планирование для сессии, начатой в Plan Mode

Основной агент самостоятельно читает инструкции проекта, нужный код
и проверки, уточняет существенные требования и готовит план. Факты,
доступные в коде или среде, проверяет сам. Не делегируй первоначальное
изучение, интервью или составление плана. Дождись решений пользователя
по блокирующим развилкам; не подменяй их предположениями.

План содержит цель, границы, принятые решения, затронутые компоненты,
последовательность изменений и проверки. До реализации он проходит
независимое ревью и подтверждение пользователя.

#### Межпровайдерное ревью

Выбери роль ревью плана из единой таблицы по фактическому провайдеру
основного агента: Anthropic → Sol, OpenAI (включая Sol) → Opus.
Используй динамический подбор и medium из таблицы, без повышения effort
из-за размера задачи. Тот же провайдер не заменяет независимое ревью.

Передай цель, итоговый план, решения пользователя, ограничения и точечные
ссылки на исходники. Не передавай всю переписку, все исходники и большие логи.
Ревьюер может читать необходимые соседние файлы; не пишет код, не редактирует
план и не делегирует дальше. Проверяет выполнимость, риски, непринятые решения,
совместимость контрактов и достаточность тестов. Возвращает только существенные
замечания с приоритетом, обоснованием и проверяемым способом закрытия;
не требует изменений ради формального наличия замечаний.

#### Замечания и подтверждение

Дождись ревью. Основной агент проверяет замечания по коду и требованиям,
корректирует план, обосновывает отклонённые замечания. Новые существенные
решения согласует с пользователем. Не запускай повторное ревью автоматически,
если поправки локальны и замечания закрыты проверяемо. Архитектурная
переработка или новые риски требуют нового раунда.

Для каждого необходимого T3-раунда создавай новый `delegate_task` с исходным
брифом, обновлённым планом, прежними замечаниями, ответами и незакрытыми
возражениями. Сохраняй отдельный taskId и уникальный clientRequestId раунда,
стабильный при повторе его запуска. Не продолжай делегированное ревью через
`t3_thread_send` на childThreadId; перед retry проверь состояние taskId.

Покажи финальный план пользователю и дождись явного подтверждения.
Положительное ревью не заменяет его. До подтверждения не реализуй;
после подтверждения поручай изменения исполнителю, сохраняя исходный режим.

### Реализация и проверка результата

В исходном Plan Mode применяй этот раздел после подтверждения плана:
основной агент координирует, читает код, проверяет diff и отчёты, но не пишет
и не исправляет код. В обычной сессии он может реализовать и проверить задачу
сам; при делегировании используй тот же процесс ниже без обязательной цепочки
плана. Роли и уровни определены один раз в таблице моделей.

#### Один исполнитель: код и тесты

Выбери одного исполнителя по таблице, по умолчанию Luna; Haiku — разрешённая
альтернатива по условиям из «Разрешённых маршрутов и ролей». Передай цель,
границы, затронутые пути, ограничения, критерии приёмки и команды проверок.
Тот же исполнитель пишет код, запускает соответствующие форматирование,
линтеры/статический анализ, сборку и тесты и исправляет непосредственно
обнаруженные проблемы в рамках retry budget. Не создавай отдельную Luna
только для запуска тестов.

Возвращай команды, exit code, короткий существенный лог ошибок и условия
воспроизведения. У каждой проверки статус PASS, FAIL или NOT_RUN с причиной.
Недоступная проверка и тесты, заблокированные сборкой, — NOT_RUN, а не успех.
Не игнорируй падения, не отключай и не ослабляй проверки ради зелёного
результата.

#### Tool-first диагностика

До создания нового агента-диагноста используй обычные инструменты проекта:
форматирование, статический анализ/линтер, компиляцию, релевантные
unit/integration тесты. Начинай с затронутых частей; расширяй до полной
сборки/набора тестов при изменении общих контрактов, зависимостей,
публичного API или перед значимым релизом. Если обязательную проверку
нельзя запустить, зафиксируй причину. Очевидную по выводу инструмента
проблему верни существующему исполнителю узким заданием; дорогой эксперт
для этого не нужен.

#### Ревью по риску и diff

После реализации и проверок основной агент читает точный итоговый diff
от зафиксированной базы и отчёт проверок. Классифицируй работу по количеству
затронутых компонентов и сервисов, изменениям контрактов, объёму и характеру
diff, наличию тестов и обратимости. Одних строк или числа файлов недостаточно.

- Небольшая или обычная безопасная правка: самостоятельное ревью основным
  агентом, без отдельного ревьюера. В исходном Plan Mode исправления всё равно
  поручаются исполнителю.
- Большое и сложное изменение: один независимый полноценный проход ролью
  ревью кода из таблицы.
- Высокий риск важнее размера diff: аутентификация, безопасность, доступ
  к данным, криптография, миграции, конкурентность или публичные API могут
  требовать независимого ревью даже при маленькой правке. Оцени последствия
  и назначь независимую проверку при существенном риске, не обходи её
  по размеру.

Передай ревьюеру задачу, критерии приёмки, краткий отчёт исполнителя, точную
базу и diff (включая незакоммиченные и новые файлы), нужные пути к исходникам.
Ревьюер сам читает соседний код при необходимости, не исправляет файлы.
Попроси только обоснованные замечания: приоритет, место, последствия,
условия воспроизведения и рекомендуемое исправление. Полная переписка
и огромные логи не нужны.

После исправления независимых замечаний повторное ревью ограничивается
изменёнными hunks и связанными местами; полный повтор нужен при изменении
архитектуры, базовых контрактов или высокорисковых областей. Не создавай
повторный раунд без необходимости проверки исправлений или новых рисков.
Каждый новый T3-раунд — отдельный `delegate_task` с исходным брифом,
обновлённым diff, предыдущими находками, ответами и незакрытыми возражениями;
новый clientRequestId раунда, стабильный при retry. childThreadId не используй
для продолжения ревью через `t3_thread_send`.

#### Бюджет исправлений и эскалация

На одну и ту же диагностированную ошибку — до двух осмысленных попыток
исправления, включая первичную. Каждый следующий цикл требует новых данных
и уточнённой гипотезы; не повторяй идентичный запрос. Веди счёт по ошибке,
не обнуляй его при создании агента или переименовании задания.

Сначала возвращай узкое задание исходному исполнителю, если продолжение
поддерживается. Проверь taskId и используй доступный механизм продолжения;
не создавай новую задачу только ради свежего контекста. Если продолжение
невозможно, передай заменяющей задаче текущее состояние и использованный
бюджет.

После двух неудач либо при неясной причине многокомпонентного сбоя допустима
одна консультация эксперта диагностики из таблицы, по возможности другого
провайдера. Передай команды, exit code, существенные ошибки, воспроизведение
и уже проверенные гипотезы. Эксперт анализирует причину, не меняет файлы.
После консультации исполнитель делает одну дополнительную корректировку
на основе новой гипотезы. Не запускай новую цепочку экспертов или новый бюджет.
Если блокер остался, прекрати циклы и покажи пользователю факты, реальные
статусы проверок, незакрытые риски и варианты продолжения.

После любого исправления снова запускай затронутые проверки; для высокого
риска — весь обязательный набор. Успех до исправления не подтверждает новый
код. В обычной самостоятельной работе те же ограничения относятся к попыткам
основного агента; создание исполнителя не обнуляет бюджет.

#### Параллелизм и интеграция

По умолчанию один активный исполнитель. Максимум два — лишь при независимых
файлах/контрактах и явной пользе; три — только по прямой просьбе пользователя.
Не дублируй одну задачу между Luna и Haiku. Параллельные изменения изолируй
рабочими деревьями через T3 `delegate_task` с `isolation: "worktree"`.
Такая задача стартует с локального коммита родителя, незакоммиченные изменения
не копируются: обеспечь доступность нужной базы до запуска.

Дождись результатов, поручай интеграцию исполнителю в исходном Plan Mode.
Итоговые проверки и ревью выполняй после интеграции, по общему diff;
разрозненные промежуточные diff не заменяют проверку результата.

#### Компактный handoff и управление задачами

Для делегирования используй краткий бриф:

```text
GOAL: <одна конкретная цель>
BASE/DIFF: <ref и область изменений>
SCOPE: <пути и разрешённые изменения>
CONSTRAINTS: <что нельзя менять и важные соглашения>
ACCEPTANCE: <3–5 проверяемых требований>
VERIFY: <команды и ожидаемые проверки>
RETURN: <изменённые файлы, статусы проверок, 3–7 строк результата, блокеры>
```

Передавай пути и ссылки, а не всю историю и исходники; полные логи запрашивай
только при нехватке данных. Явно запрещай вторичное делегирование без
разрешения основного агента. Сохраняй taskId и проверяй состояние перед
retry, не дублируй активные вызовы; clientRequestId стабилен для повторов
одного запуска.

Основной агент отвечает за интеграцию и итоговую оценку. Сообщай завершение
и успешные проверки только при выполненных критериях, закрытых существенных
замечаниях и PASS обязательных проверок итогового кода. При FAIL/NOT_RUN
сообщай фактический результат и причину, не объявляй все проверки успешными.

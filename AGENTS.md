# Lognara

Lognara содержит отдельные Rust-crates agent, relay, core и общий spool. Агент принимает HTTP, файлы и stdout/stderr; relay нормализует события, core хранит и ищет логи. Актуальные контракты описаны в Obsidian и подтверждаются исходниками.

### Чтение памяти

- Перед работой прочитай `Index.md` и относящиеся к задаче заметки. При обычном обновлении изучай затронутые исходники; полный обзор нужен при общих архитектурных изменениях или явном запросе на полную актуализацию.
- Проверяй сведения по актуальному коду, конфигурации и документации. Память не заменяет проверку исходников.
- Для работы с памятью используй доступные средства поиска и работы с файлами; при наличии `rg` предпочитай его. Навык не требует конкретного инструмента, субагента или модели.

### Обновление памяти

- Храни назначение и границы компонентов, значимые публичные контракты, зависимости, взаимодействия, ключевые потоки, ограничения и подтверждённые причины решений. Указывай реальные пути исходников и важные символы.
- Описывай контракты по смыслу; не копируй код, полные списки методов и полей и очевидные детали реализации. Внутренние вспомогательные функции, косметические изменения и рефакторинг без изменения поведения или архитектуры не требуют обновления памяти.
- Обновляй описанное поведение на месте при изменении контракта, потока, зависимости или ограничения. Удалённые контракты и неверные сведения убирай без зачёркиваний и датированных записей.
- Перед созданием заметки ищи существующую по назначению, названию и исходникам. Дополняй её, сохраняя полезные сведения и ручные дополнения. Описание контракта или основания решения храни в одном месте, из остальных заметок ссылайся на него.
- Значимые компоненты размещай в папках фактических доменов. Добавляй новую значимую заметку в навигацию `Index.md`; каждая такая заметка должна быть достижима из индекса напрямую или через связанные заметки.

- Устройство компонента подтверждай реализацией. Причины выбора подтверждай документацией, объясняющими комментариями или словами пользователя; неизвестные важные причины отмечай как не задокументированные. `Decisions.md` создавай только при необходимости отдельного подробного объяснения нескольких решений.

## Проверка затронутых компонентов

- Для изменений agent, relay, core, dock и общего spool определяй зависимые места вызова, HTTP-клиенты, фоновые задачи и конфигурацию Docker Compose. Каждый Rust-crate собирается отдельно; общего Cargo workspace нет.
- При изменении MessagePack + zstd между agent → relay → core, HTTP/JSON API, SSE, форматов spool/WAL/Parquet, схем SQLite или конфигурации `LOGNARA_*` проверяй производителей и потребителей. Учитывай совместимость wire-фикстур в тестах relay и core.
- Учитывай React/TypeScript-клиент в `Lognara-dock/web/`, Rust-прокси dock и CLI агента там, где изменение их затрагивает.
- Сохраняй совместимость публичных контрактов и сохранённых данных без явной необходимости её менять. При добавлении создания, включения или подключения проверяй необходимость удаления, отключения и восстановления.
- Меняй только затронутые компоненты и явно указывай, что не проверено.

## Архитектурные границы

- HTTP-обработчики axum в agent, relay, core и dock принимают и проверяют запрос, вызывают соответствующий сервис или модуль и формируют ответ. Не добавляй в транспортный слой самостоятельную бизнес-логику.
- Сохраняй разделение стадий конвейера: сбор в agent, нормализация в relay, хранение и запросы в core, сессии и проксирование в dock.
- Перед созданием общей абстракции проверяй `Lognara-spool/`; не переноси туда логику только ради одного потребителя.
- Не изменяй публичные контракты без проверки обратной совместимости у зависимых компонентов.

## HTTP и durable-доставка

- Сохраняй подтверждение agent/relay только после durable-записи всей принятой группы в spool, а core — после fsync WAL. Не удаляй очередь до успешного ACK следующего сервиса.
- Учитывай повторы при сбоях и восстановлении: подготовленные пачки повторяются теми же байтами, core дедуплицирует тело по SHA-256; повтор исходного запроса может создать новые ID событий.
- Сохраняй квоты диска, ограничения тела и распаковки, резервы памяти и поведение при перегрузке. Не добавляй блокирующие операции в горячий асинхронный путь tokio; используй существующие blocking-работники.
- Учитывай отмену, таймауты и ошибки HTTP-вызовов, включая завершение фоновых операций при остановке.
- Сохраняй проверку персонального токена агента в relay до чтения тела и распаковки. Не меняй разделение relay/admin/query-токенов без обоснования; query/admin-токены core должны оставаться в dock и не попадать в браузер.

## Проверка изменений

- Проверяй минимальный достаточный набор: изменённый компонент, затронутые тесты и зависимые контракты. Не запускай полную сборку всех crate без необходимости; для сквозных изменений расширяй проверку.
- Для затронутых Rust-crate используй проверки из `.github/workflows/ci.yml`: `cargo fmt --all --check`, `cargo clippy --locked --all-targets --all-features -- -D warnings`, `cargo build --locked`, `cargo test --locked --all-features`. Запускай их из каталога crate; у core `--all-features` включает `crash-tests`.
- При изменении памяти agent/relay проверяй соответствующий `tests/check-memory-profile.py`. Для веб-клиента используй `npm run build`, `npm test` и относящиеся к изменению Playwright-сценарии через `npm run test:e2e` из `Lognara-dock/web/`.
- Для исправления бага по возможности добавляй воспроизводящий тест; для новой значимой логики — проверки ожидаемого поведения и существенных ошибок. Не создавай тесты, лишь повторяющие реализацию или очевидную передачу параметров.
- В асинхронных тестах предпочитай ожидание наблюдаемого события или состояния произвольным задержкам.
- Не сообщай, что тесты прошли, если они не запускались. Если проверка невозможна, указывай конкретную причину.

## Безопасность окружения

- Не запускай миграции и не изменяй рабочие SQLite-базы core/dock без явного разрешения.
- Не выполняй `docker compose down -v`, удаление volumes, spool, WAL, сегментов или пользовательских данных без разрешения.
- Не останавливай процессы по шаблону имени через `pkill -f` или аналогичные команды; останавливай только процессы, принадлежность которых текущей задаче подтверждена.
- Не изменяй секреты, токены, реальные конфигурации и переменные окружения (`.env`, `Example/.env`, htpasswd, `LOGNARA_*`) без необходимости и разрешения.
- Для тестов используй отдельное окружение и изолированные данные. Не коммить временные файлы агента, диагностические дампы, логи и исследовательские заметки.

## Производительность

- Для изменений в горячем пути оцени влияние на задержки, память, CPU и количество сетевых обращений.
- Избегай лишних запросов к SQLite, повторной сериализации и ненужных аллокаций; учитывай стоимость поиска Tantivy и аналитики DataFusion/Parquet.
- Не передавай крупные объекты по HTTP/SSE без необходимости и не блокируй асинхронный код синхронным ожиданием.
- В React избегай ненужных перерисовок, постоянных анимаций и полной переработки списков при небольших изменениях.
- Не оптимизируй без доказанной причины: сначала установи проблему, затем устраняй её.

## Создание Pull Request

### Когда создавать PR

- Создавай Pull Request на GitHub только по явному запросу пользователя. Такой запрос разрешает необходимую отдельную ветку и push, если пользователь отдельно не запретил эти действия.
- Если пользователь просит только подготовить PR, не выполняй push и создание PR автоматически.
- Один PR должен решать одну логически связанную задачу; не объединяй несвязанные исправления, рефакторинг и новые функции. Не создавай дубликат уже открытого PR для этой задачи.

### Ветки и коммиты

- Целевая ветка по умолчанию — `master` (`origin/HEAD`). Другие долгоживущие ветки и схема продвижения изменений не подтверждены; не придумывай их. Учитывай явно указанную пользователем целевую ветку.
- Для PR используй отдельную рабочую ветку от актуальной целевой, сохраняя принятую схему `t3/<short-description>`. Если задача уже выполняется в отдельной ветке, используй её. Не изменяй `master` напрямую ради создания PR.
- Не включай в PR чужие незакоммиченные изменения. Соблюдай русский язык и ограничения сообщений коммитов из раздела Git; Conventional Commits и обязательные scope в проекте не установлены.
- Название PR пиши по-русски, кратко описывая конкретный результат. Примеры: `Исправить повторную доставку пачек relay`, `Добавить фильтр окружения в графики Dock`, `Обновить правила памяти проекта`.

### Перед созданием PR

1. Проверь полный diff относительно целевой ветки: все файлы относятся к задаче, нет случайного форматирования и несвязанных правок.
2. Проверь корректность и совместимость изменений, запусти доступные целевые тесты и сборки по инженерным правилам.
3. Убедись, что необходимые изменения памяти в `Obsidian/LognaraVault/` внесены.
4. Проверь отсутствие секретов, токенов и временных файлов.

Не запускай автоматически всю сборку монорепозитория: проверяй затронутые crate и веб-клиент, расширяя объём при необходимости.

### Описание PR

Шаблон PR в репозитории не обнаружен. Используй следующую структуру, пропуская пустые и неприменимые разделы:

**Summary**

- Что изменено, какую проблему решает и какие технические решения нужны для понимания изменения.

**Testing**

- Какие тесты, проверки и сборки выполнены, их результаты; что не проверено и почему.

**Compatibility & Risks**

- Какие части agent, relay, spool, core, dock и веб-клиента затронуты.
- Изменения MessagePack/HTTP/JSON/SSE-контрактов, форматов сохранённых данных, SQLite или конфигурации.
- Ограничения, риски и необходимые действия при развёртывании.

**Visual Changes** (для UI)

- Скриншоты до и после, если доступны; для существенных изменений анимаций — короткая видеодемонстрация, если возможно.

### После создания PR

- Убедись, что PR направлен в правильную ветку.
- Проверь GitHub Actions в `.github/workflows/ci.yml`, включая итоговую проверку `CI passed`; не утверждай, что CI прошёл, до подтверждения GitHub. Публикация образов запускается после успешного CI только при push в `master` и не является проверкой PR.
- Если пользователь попросил сопровождать PR, следи за новыми результатами CI и комментариями после последнего изменения.
- Проверяй замечания автоматических ревьюеров по исходникам. Исправляй подтверждённые проблемы, для ложных срабатываний указывай техническую причину.
- Не выполняй merge без явного разрешения пользователя.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.

## Оркестрация субагентов

### Исходный режим сессии

Правила оркестрации зависят от того, **в каком режиме сессия началась**, а не только от её текущего режима.

- **Сессия началась в Plan Mode:** обязательна цепочка самостоятельного планирования, уточнений, независимого ревью плана, подтверждения пользователем, делегированной реализации, ревью кода и сборки с тестами. Основной агент код не пишет.
- **Сессия началась без Plan Mode:** выполняй поставленную пользователем задачу обычным способом. Консультация наставника и делегирование кода или проверок доступны по необходимости, как описано ниже.

Определи исходный режим по сведениям о запуске или истории текущей сессии и сохраняй его в контексте работы, включая передачу контекста после сжатия. `interactionMode` из текущего ответа T3 показывает текущий режим; после переключения он не доказывает, каким был режим при запуске. Если исходный режим установить нельзя и это влияет на выбор процесса, уточни его у пользователя, не выбирая ветку по догадке.

Само переключение режима, появление краткого плана в ответе или создание плана субагентом не меняет исходный режим сессии. Изменить согласованный порядок работы можно по явному указанию пользователя.

### Разрешённые провайдеры и harness'ы

Используй только модели OpenAI через официальный harness Codex и модели Anthropic через официальный harness Claude Code. **OpenRouter и OpenCode запрещены**: это все модели провайдера OpenCode (`providerInstanceId` `opencode`), включая модели с префиксом `openrouter/`, даже если через них доступна нужная модель OpenAI или Anthropic. Запрет действует для всех ролей субагентов в обоих режимах сессии, включая консультации, ревью, реализацию и тестирование.

Перед делегированием проверь фактического провайдера и harness по T3 `orchestrator_capabilities`; одного имени модели недостаточно. Если разрешённый вариант недоступен или его нельзя подтвердить, сообщи пользователю и согласуй замену в пределах разрешённых провайдеров и harness'ов. Не используй OpenRouter или OpenCode как запасной маршрут.

### Соответствие ролей моделям

| Роль | Модель | Рассуждение |
|------|--------|-------------|
| Наставник в сессии без Plan Mode | `gpt-6.1-sol` (Codex) или `claude-opus-5-5` (Claude) | `high` |
| Код и тесты после изучения задачи в сессии без Plan Mode | Luna 6+, базовая `gpt-6-luna` (Codex) | `max` |
| Независимое ревью плана (Plan Mode) | `gpt-6.1-sol` (Codex) | `high`; `xhigh` для большой и сложной задачи |
| Реализация, сборка, тесты и простые исправления (Plan Mode) | Luna 6+, базовая `gpt-6-luna` (Codex) | `max` |
| Ревью кода (Plan Mode) | `claude-sonnet-5-5` (Claude) | `high` |
| Сложные исправления (Plan Mode) | `gpt-6.1-sol` (Codex) | `medium` |

- Точные идентификаторы моделей и провайдеров бери из каталога T3 `orchestrator_capabilities`. Отличай идентификатор от отображаемого названия и сохраняй оба для делегирования.
- Передавай уровень рассуждения явно. В каталоге Codex настройка называется `reasoningEffort`, у Claude — `effort`; сверяй имена и значения с каталогом.
- Сравнивай версии Luna численно, а не по порядку в каталоге или строковой сортировке. Не считай другую модель новой Luna только из-за похожего названия.
- Если модель, уровень или возможность запуска субагента недоступны, сообщи пользователю и согласуй замену. Не подменяй модель и не снижай уровень рассуждения молча.

### Сессия без Plan Mode

Основной агент изучает задачу и нужный код, выполняет запрос пользователя и проверяет результат. Он может самостоятельно писать и исправлять код. При неоднозначностях, требующих решения пользователя, задавай вопросы. Обязательное утверждение плана, ревью плана и цепочка с Sonnet из правил Plan Mode к этой ветке не применяются.

#### Консультация наставника при проблемах

Если возникла проблема и нужен дополнительный взгляд, можно создать субагента-наставника **Sol 6.1 (`gpt-6.1-sol`) на `high`** или **Opus 5.5 (`claude-opus-5-5`) на `high`**. Выбери одного из них с учётом доступности и указаний пользователя. Консультация необязательна.

Передай вопрос, контекст задачи, относящийся к проблеме код, наблюдаемые ошибки и уже проверенные гипотезы. Попроси объяснение и рекомендации; наставник не изменяет файлы. Основной агент оценивает ответ и решает, как продолжать работу. Новый пользовательский выбор уточняй у пользователя.

#### Делегирование кода и тестов после изучения задачи

Если тема изучена достаточно, чтобы передать конкретное задание, можно поручить написание кода и запуск сборки или тестов субагентам **Luna 6 или новее на `max`**. Выбирай новейшую доступную модель семейства Luna версии не ниже 6, поддерживающую `max`; базовая модель — `gpt-6-luna`. Полный утверждённый план для такого делегирования не требуется.

Передай цель, нужные исходники, границы изменений, ограничения и критерии готовности. Для проверки передай также необходимые команды и область изменений. Попроси отчёт о выполненной работе; при сбоях — что и где сломалось, результаты команд и существенные сообщения об ошибках. Основной агент проверяет отчёты и доводит исходную задачу до завершения. Не считай пропущенные или недоступные проверки успешными.

Используй нативный инструмент для того же провайдера, если он поддерживает модель и уровень; для другого провайдера или неподдерживаемой модели — T3 `delegate_task`. Сохраняй идентификаторы задач и не дублируй активную работу. Создавай дочерние задачи, а не отдельные основные беседы.

### Сессия, начатая в Plan Mode: планирование

Эти правила применяются только к сессиям T3 Code, изначально начатым в Plan Mode. До подтверждения финального плана пользователем не начинай реализацию. Переход в режим реализации после подтверждения плана не отменяет выбранную для этой сессии цепочку оркестрации.

#### Самостоятельная подготовка

Основной агент сам изучает поставленную задачу, инструкции проекта, соответствующий код и существующие проверки. Не делегируй изучение задачи, чтение кода, интервью с пользователем или написание первоначального плана субагентам.

Выяви развилки, неоднозначности, недостающие требования и зависимости до начала реализации. Факты, которые можно выяснить по коду или среде, проверь самостоятельно. Решения, требующие выбора пользователя, обсуждай с ним, предлагая рекомендуемый вариант и объясняя последствия. Дожидайся ответа на существенные вопросы; не подменяй его предположением.

Если установлен `grill-me` или доступен аналогичный навык для уточнения требований, прочитай его инструкции и используй при интервью. Если это навык-обёртка, прочитай также навык, на который он ссылается. Если подходящего навыка нет, проведи уточнение самостоятельно; установка навыка не требуется. При использовании такого интервью задавай вопросы по одному и разрешай зависимые решения последовательно.

Составь план реализации на основе изученного кода и ответов пользователя. Укажи цель, границы работы, принятые решения, затрагиваемые компоненты, последовательность изменений и способ проверки результата. Перед независимым ревью убедись, что нет открытых вопросов к пользователю и неразрешённых неоднозначностей, обнаруженных на этом этапе.

#### Независимое ревью готового плана

Только после подготовки плана и завершения уточнений создай субагента для независимого ревью. Модель — Sol 6.1 (`gpt-6.1-sol`):

- `high` — обычная задача.
- `xhigh` (Extra High) — большая и сложная задача: например, несколько взаимосвязанных подсистем, изменение контрактов или сложная миграция.

Получи актуальный каталог через T3 `orchestrator_capabilities` и проверь модель, провайдер, возможность запуска субагента и доступные настройки рассуждения. Передай выбранный уровень явно, а не полагайся на значение по умолчанию. В каталоге Codex это настройка `reasoningEffort`. Если нужная модель или уровень недоступны, сообщи пользователю и согласуй замену; не пропускай ревью и не подменяй модель молча.

Используй инструменты создания субагентов, а не отдельной основной беседы. Для того же провайдера предпочитай нативный инструмент, если он поддерживает выбранную модель и уровень рассуждения. Иначе используй T3 `delegate_task` с выбранными `providerInstanceId`, `model` и настройками рассуждения.

Передай ревьюеру полный план, исходную задачу, согласованные требования, решения пользователя, ограничения и необходимые пути к исходникам. Не рассчитывай на автоматическое наследование истории беседы. Задача ревьюера — проверить полноту, выполнимость, соответствие коду, пропущенные развилки, риски и достаточность проверок. Ревьюер может читать код, но не изменяет файлы, не начинает реализацию и не запускает своих субагентов.

Попроси вердикт о готовности плана и конкретные замечания с обоснованием: что исправить и какие решения требуют ответа пользователя. Дождись завершения ревью перед выдачей финального плана.

Для T3-делегирования сохраняй `taskId`; проверяй состояние существующей задачи, прежде чем запускать замену. При необходимости нового раунда ревью создай новую задачу через `delegate_task`, передав исходный запрос, обновлённый план, предыдущие замечания, ответы и оставшиеся возражения. У каждого раунда отдельный `clientRequestId`, стабильный при повторах его запуска. Не продолжай ревью через `t3_thread_send` на `childThreadId`.

#### Разрешение замечаний и финальный план

Основной агент оценивает замечания по коду, требованиям и принятым решениям. Простые поправки к плану, не создающие нового выбора и не меняющие согласованные требования, внеси самостоятельно. Отклонённые замечания обоснуй; вердикт ревьюера сам по себе не заменяет проверку.

Если ревью выявило новую развилку, неоднозначность или проблему, решение которой требует выбора пользователя, задай уточняющий вопрос и дождись ответа. Не выбирай за пользователя только ради завершения плана.

После разрешения замечаний и новых вопросов обнови план и выдай его пользователю на подтверждение. Финальный план должен включать принятые решения и проверки, без открытых вопросов, блокирующих реализацию. Подтверждение плана не заменяется положительным вердиктом субагента.

### Сессия, начатая в Plan Mode: реализация

Эти правила применяются только к сессиям T3 Code, изначально начатым в Plan Mode, при реализации подтверждённого пользователем плана. Они продолжают действовать после переключения из планирования в реализацию. Основной агент отвечает за план и координацию: распределяет работу, контролирует выполнение, оценивает отчёты и сообщает результат. Он сам не пишет и не исправляет код, включая тесты. Изменения кода, интеграцию изменений и разрешение конфликтов поручай субагентам.

#### Выбор моделей

Перед делегированием получи актуальный каталог T3 через `orchestrator_capabilities`. Проверь возможность запуска субагентов у выбранных провайдеров и поддержку требуемых уровней рассуждения.

- Реализация, сборка, тесты и простые исправления: **Luna 6 или новее** с рассуждением **`max`**. Базовый идентификатор — `gpt-6-luna`.
- Ревью кода: **Sonnet 5.5**, `claude-sonnet-5-5`, рассуждение **`high`**.
- Сложные исправления: **Sol 6.1**, `gpt-6.1-sol`, рассуждение **`medium`**.

#### 1. Делегировать написание кода

Создай субагента Luna 6+ на `max` и передай подтверждённый план, исходную задачу, решения пользователя, инструкции проекта, границы изменений, нужные пути и критерии готовности. Не рассчитывай на автоматическую передачу истории беседы. Попроси отчёт об изменённых файлах, реализованных пунктах плана, отклонениях и оставшихся проблемах.

Если в плане есть независимые части, например в двух или трёх отдельных проектах, можно запустить несколько субагентов Luna 6+ на `max` параллельно. Перед запуском проверь отсутствие пересечений по файлам, общим контрактам и зависимостям. Назначь каждому свою область изменений; при необходимости используй изолированные рабочие копии. Зависимые или пересекающиеся части выполняй последовательно.

Основной агент отслеживает выполнение и разрешает организационные вопросы. Если возник новый выбор, меняющий подтверждённый план или требования, обсуди его с пользователем до выполнения соответствующей части.

#### 2. Передать завершённый код на ревью

Дождись завершения единственного исполнителя или всех параллельных исполнителей. Если изменения находятся в разных рабочих копиях, поручай их интеграцию субагенту Luna 6+ на `max` до итогового ревью.

Создай субагента **Sonnet 5.5 на `high`** для изучения и ревью написанного кода. Передай план, требования, границы итоговых изменений, отчёты исполнителей и пути к исходникам. Для нескольких проектов включи все затронутые проекты и их взаимодействия в область ревью.

Ревьюер проверяет соответствие плану, ошибки поведения, пропущенные случаи, проблемы взаимодействия компонентов и регрессии. Он не исправляет код. Попроси вердикт и отчёт по каждой проблеме: серьёзность, файл и место, объяснение ошибки, условия воспроизведения и рекомендуемое исправление. Не требуй находить проблемы, если обоснованных замечаний нет.

#### 3. Запустить сборку и тесты

После получения ревью создай отдельного субагента **Luna 6+ на `max`** для запуска сборки и подходящих тестов итогового кода. Передай инструкции проекта, область изменений, требуемые проверки из плана и замечания ревью. Проверки нужны и при наличии замечаний: их отчёт дополняет ревью.

Субагент использует предусмотренные проектом команды и не исправляет исходники, не отключает проверки и не ослабляет тесты ради успешного результата. Попроси отчёт с командами, результатами, кодами завершения, выполненными и пропущенными проверками. При сбоях он сообщает, что и где сломалось, с существенными фрагментами ошибок и местами в коде, если они определены. Предположение о причине должно быть отделено от установленного факта.

Если сборка блокирует запуск тестов или среда не позволяет выполнить проверку, это указывается в отчёте. Пропущенные проверки не считаются успешными.

#### 4. Исправить проблемы новым субагентом

Если ревью выявило проблемы или сборка и тесты завершились с ошибками, основной агент собирает замечания в конкретное задание и создаёт нового субагента для исправления:

- **Luna 6+ на `max`** — локальная и понятная проблема с ограниченным исправлением в рамках согласованного плана.
- **Sol 6.1 на `medium`** — сложная проблема: неясная причина, несколько взаимодействующих компонентов, необходимость пересмотреть технический подход.

Оценивай сложность по содержанию проблемы, а не только по количеству ошибок. Передай новому исполнителю исходный план, текущие изменения, отчёты ревью и проверок, условия воспроизведения, ограничения, конкретные указания и критерии исправления. Новый исполнитель не должен восстанавливать контекст по догадкам. Основной агент сам исправления не вносит.

Если исправление требует нового продуктового выбора или изменения согласованных требований, сначала получи решение пользователя. После исправления повтори ревью у Sonnet 5.5 `high`, затем сборку и тесты у Luna 6+ `max` для обновлённого кода. Успех прежних проверок не подтверждает корректность последующих изменений. Не запускай без изменений одинаковые попытки исправления: учитывай новые результаты и уточняй задание.

#### Управление субагентами и завершение

Используй инструменты делегирования дочерних задач. Для того же провайдера предпочитай нативный инструмент, если он поддерживает требуемую модель и уровень рассуждения. Для другого провайдера или неподдерживаемой нативным инструментом модели используй T3 `delegate_task`. Отдельные основные беседы через `t3_thread_launch` или `create_threads` не заменяют субагентов. Исполнители не делегируют работу дальше без указания основного агента.

Сохраняй идентификаторы задач и проверяй состояние перед повторным запуском, чтобы не дублировать активную работу. Для каждого T3-раунда ревью создавай новую задачу через `delegate_task`, передавая исходный запрос, обновлённые изменения, предыдущие замечания, ответы на них и нерешённые возражения. Каждый раунд имеет отдельный `clientRequestId`, стабильный при повторе его запуска. Не продолжай ревью через `t3_thread_send` на `childThreadId`.

Сообщай пользователю, что работа завершена и проверки прошли, только после выполнения плана, разрешения замечаний ревью и успешного завершения требуемой сборки и тестов итогового кода. Кратко укажи, что сделано и какие проверки выполнены. Если остались проблемы или проверки недоступны, сообщи их явно вместо утверждения, что всё в порядке.

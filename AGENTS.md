# Lognara

Репозиторий находится в стадии заготовки: `README.md` содержит только название Lognara. Сейчас нет исходного кода и манифеста зависимостей; `.gitignore` содержит шаблонные правила Cargo, но это не подтверждает технологический стек или назначение проекта.

## База знаний — Obsidian

| Файл | Содержание |
|------|------------|
| `Obsidian/LognaraVault/Index.md` | Главная точка входа и навигация по базе знаний. |
| `Obsidian/LognaraVault/Architecture.md` | Подтверждённый стек, структура, компоненты и сквозные потоки. |
| `Obsidian/LognaraVault/Repository/RootFiles.md` | Исходное состояние README, LICENSE и .gitignore. |

## Правила обновления Obsidian

- При изменении функциональности файла или метода найди заметку компонента и обнови описание. Устаревший метод помечай как `~~methodName~~ (удалён: YYYY-MM-DD)`, новый добавляй в таблицу методов.
- При добавлении файла или компонента создай или дополни заметку в папке фактического домена и добавь ссылку в `Index.md`. Для крупных компонентов (более 10 файлов или сложная структура) создай `-ProjectMap.md`.
- При изменении общей архитектуры, зависимостей, конфигурации или точек входа обнови `Architecture.md`.
- Changelog в vault не веди — историю изменений хранит git.
- Краткое описание метода: `methodName(param: Type): ReturnType — одна строка о назначении`.

## Имена файлов Obsidian

- Создавай папки и файлы внутри vault только с английскими именами, используя латинские буквы, цифры и дефисы. Текст заметок может быть на русском.
- Перед переименованием заметки проверь backlinks и обнови все ссылки. Имена существующих заметок в этом vault: `Index.md`, `Architecture.md` и `Repository/RootFiles.md`.

## Правила чтения файлов проекта

- Для исследования большого репозитория используй Explore (haiku), чтобы собрать дерево файлов, домены и точки входа. В небольшом репозитории прочитай README, манифесты и целевые файлы напрямую.
- Перед изменением кода прочитай целевые файлы и связанные места вызова. Для обновления базы знаний прочитай существующую заметку и дополняй её, не пересоздавая с нуля.
- Не делай выводов о стеке, назначении или компонентах по косвенным признакам; пока в репозитории нет исходников и манифеста, считай эти сведения неподтверждёнными.

## Правила работы с Git репозиторием

- Работай в текущей ветке. Создавай отдельную ветку только по прямому указанию.
- Пиши заголовки и описания коммитов только на русском языке. Не используй длинное тире (— или –); обычный дефис допустим.
- Описывай изменения кратким списком максимум из 6 пунктов. Всё сообщение коммита, включая заголовок и описание, должно быть не длиннее 200 символов.
- Если изменения не помещаются в этот объём, раздели их на несколько самостоятельных коммитов.
- В большой задаче с планом создавай отдельный коммит после каждого завершённого этапа. Не отправляй коммиты в удалённый репозиторий без прямой просьбы.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.

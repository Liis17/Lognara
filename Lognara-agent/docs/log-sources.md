# Файлы и stdout/stderr

Один агент собирает логи одной программы через HTTP, файлы и потоки. Для Nginx, PostgreSQL, Seq и MinIO используются одинаковые сборщики; настройка определяет расположение и формат данных. Специального разбора полей этих приложений нет.

## Запуск

Обязательные переменные `LOGNARA_SERVICE`, `LOGNARA_SERVER`, `LOGNARA_BACKEND`, `LOGNARA_RELAY_TOKEN`, URL relay и постоянный spool задаются как в [README](../../README.md#быстрый-старт).

```sh
# Только HTTP и файлы
LOGNARA_SOURCES_FILE=/etc/lognara/sources.json lognara-agent

# HTTP, настроенные файлы и оба потока программы
lognara-agent run -- /path/to/program argument1 argument2
```

Аргументы передаются непосредственно программе. Shell используется только если вы явно запускаете `/bin/sh`. В `run` stdout и stderr включаются как текстовые источники с ID `stdout` и `stderr`. Определение потока в JSON заменяет его настройки по умолчанию. В обычном режиме stdout/stderr в конфигурации запрещены. HTTP-вход работает в обоих режимах.

Агент проверяет конфигурацию, открывает spool/checkpoint, устанавливает обработчики сигналов и HTTP-порт до запуска программы. Ошибка старта не запускает программу. Рабочий каталог, аргументы и окружение наследуются; из окружения программы удаляется `LOGNARA_RELAY_TOKEN`. Это режим серверного foreground-процесса без интерактивного TTY. Программа автоматически не перезапускается.

## JSON-конфигурация

`LOGNARA_SOURCES_FILE` необязательна. Настройки читаются один раз при запуске; hot reload отсутствует. Пример:

```json
{
  "sources": [
    {
      "id": "app-files",
      "type": "file",
      "format": "text",
      "include": ["/var/log/app/*.log*"],
      "exclude": ["/var/log/app/debug.log*"],
      "start_at": "beginning",
      "multiline": {"start_pattern": "^[0-9]{4}-", "flush_timeout_ms": 1000}
    },
    {"id": "app-json", "type": "stdout", "format": "ndjson"}
  ]
}
```

Этот пример содержит stdout и требует `run`. Для обычного запуска удалите второе определение.

| Поле | Контракт |
|---|---|
| `id` | Уникальный стабильный ID, 1–64 ASCII-символа: буквы, цифры, `-_.`. Сохраняйте ID между перезапусками. |
| `type` | `file`, `stdout` или `stderr`; максимум одно определение каждого потока. |
| `format` | `text` по умолчанию или `ndjson`. |
| `include` | Непустой массив абсолютных путей/шаблонов для файла. |
| `exclude` | Необязательный массив абсолютных шаблонов для файла. |
| `start_at` | `beginning` по умолчанию или `end`, только для файлов. Применяется при первом обнаружении на старте; checkpoint имеет приоритет. Новые файлы в работающем процессе читаются с начала. |
| `multiline` | Только для `text`: `start_pattern` и положительный `flush_timeout_ms` (по умолчанию 1000). Regex сопоставляется с физической строкой без LF/CRLF; классы `\d`, `\w` и `\s` используют ASCII. |

Неизвестные поля и невалидные значения вызывают ошибку старта. Максимум 32 источника, включая автоматически добавленные потоки; JSON не больше 256 KiB, суммарно не больше 64 шаблонов на источник. Пути не больше 4096 байт. `*`, `?` и классы `[...]` допускаются только в имени файла; `**` и рекурсивный обход запрещены.

При использовании crate `Config::from_env()` читает основные переменные; вызывайте `Config::load_sources(path, capture)` отдельно либо задавайте проверенный `Config.sources`. Бинарник делает это автоматически.

## Форматы и происхождение

Текстовая завершённая строка становится записью; LF/CRLF удаляется, пустые строки сохраняются. Невалидный UTF-8 передаётся как `Binary`. В NDJSON каждая строка содержит одно JSON-значение (включая массив как одно значение); исходный JSON сохраняется без перекодирования. Ошибочная JSON-строка становится текстом с диагностикой.

В multiline совпадающая строка начинает событие, следующие строки присоединяются с исходными переводами строк. Таймер завершает накопленное событие только на текущем EOF без новых данных и без незавершённой физической строки. EOF потока завершает и строку без LF. Активный файл ожидает LF; после ротации и 5 секунд покоя его последний хвост завершается.

Строки/события разбиваются на фрагменты не больше `min(LOGNARA_MAX_RECORD_BYTES, 512 KiB)`. UTF-8 режется по границам символов; фрагменты NDJSON становятся текстом или байтами. Порядок сохраняется внутри файла или потока; общего порядка stdout и stderr нет. `received_at` означает время сбора, а не обязательно время события приложения.

`Record.origin` необязателен. Старые spool-записи читаются, а HTTP-записи без origin сохраняют прежний wire-формат. Relay добавляет к событию атрибуты:

| Атрибут | Значение |
|---|---|
| `lognara.source` | ID источника |
| `log.file.path` | Фактический канонический путь файла |
| `log.stream` | `stdout` или `stderr` |
| `log.origin.offset`, `log.origin.end` | Полуинтервал исходных байтов `[offset, end)`, включая удалённые разделители |
| `log.fragment.index`, `log.fragment.continued` | Индекс с нуля; `continued=true` означает, что событие продолжается следующим фрагментом |

Эти служебные атрибуты имеют приоритет над одноимёнными полями payload. Payload на входе relay сохраняется исходным; дальнейшие общие правила нормализации relay прежние. Парсеры специфичных полей приложений и изменения core не требуются.

## Файлы, checkpoint и ротация

Агент опрашивает каталоги раз в секунду, обрабатывает известные файлы раньше новых и читает их по очереди. Несуществующий файл ждёт; ошибки доступа диагностируются с ограничением частоты и повторяются. Нужны права чтения файла и прохода по каталогам. При временном отказе обхода сохранённые позиции не удаляются.

Открываются только обычные файлы, включая ссылки на них. FIFO, устройства, сокеты, ссылки на `/dev/stdout`/`stderr`, архивы `.gz/.zst/.xz/.bz2/.zip` и собственный spool исключаются. Один inode читается один раз. При пересечении источников первая настройка владеет файлом; конфликт диагностируется. Одновременное чтение файла и потока с одинаковыми сообщениями создаёт дубликаты.

При заполнении 75% дисковой квоты или числа записей файловый сбор приостанавливается, оставляя место потокам. Отказ relay с остановкой admission также приостанавливает файлы. Исходные файлы остаются местом хранения непрочитанных данных.

Позиции хранятся в `spool/sources.checkpoint` под общей блокировкой spool. Сначала группа записывается и синхронизируется в spool, затем checkpoint атомарно заменяется с fsync файла и каталога. Неполное событие не продвигает позицию; для уже сохранённых фрагментов хранится состояние продолжения. Ошибка checkpoint приостанавливает файловый сбор и повторяет сохранение позиции без повторного добавления группы в работающем процессе. Повреждённый checkpoint вызывает ошибку старта, автоматического сброса нет.

При переименовании агент дочитывает старый дескриптор и обнаруживает новый файл. После перезапуска ищет сохранённый inode среди несжатых соседних файлов, проверяет идентификаторы, SHA-256 префикса до 1024 байт и последних до 256 байт перед checkpoint. Обнаруженное усечение/изменение сбрасывает позицию с предупреждением. Неоднозначная идентичность допускает перечитывание, поэтому доставка файлов имеет семантику at-least-once: crash между spool и checkpoint может дать повторы.

Рекомендуется ротация переименованием с сохранением несжатых файлов до дочитывания. `copytruncate`, удаление, сжатие непрочитанных файлов и перезапись между опросами ограничивают гарантии. Ограничения: 256 отслеживаемых файлов, 64 открытых лог-файла; доступные по пути дескрипторы переоткрываются для обслуживания остальных файлов. Если все 64 удерживают удалённые/недоступные inode, новые файлы ждут с диагностикой.

## Потоки и остановка

Потоки читаются независимо фиксированными блоками. При полном spool, отказе диска/admission или перегрузке очередь не задерживает дочернюю программу: неподтверждённые данные отбрасываются, pipe продолжает освобождаться. После разрыва накопленное событие сбрасывается; остаток оборванной строки не склеивается со следующим событием.

В stderr агента периодически и при остановке выводятся накопленные счётчики `dropped_bytes`, `dropped_events`, `dropped_fragments`, `stream_gaps`, `dropped_raw_chunks`, `shutdown_cutoffs`, `echo_dropped_bytes`. Байты, целые разобранные события и разрывы до разбора считаются отдельно. Количество событий в отброшенном сыром блоке неизвестно; непрочитанные байты при ограничении дочитывания также неизвестны. Счётчики процесса не сохраняются между перезапусками и не передаются через старое поле `Batch.dropped`.

Вывод дублируется в консоль отдельными ограниченными очередями, поэтому попадает в `docker logs`, если драйвер поддерживает его. Медленная консоль может терять копию вывода; её потери считаются отдельно. Диагностика агента тоже использует неблокирующий writer и при заблокированном stderr может теряться. Она не попадает обратно в захват программы. Персистентность гарантируется для уже сохранённых записей; захват потоков при перегрузке работает best effort.

TERM, INT, QUIT, HUP, USR1 и USR2 пересылаются основному процессу. TERM/INT/QUIT начинают остановку: сбор сохраняется до выхода программы, через 10 секунд оставшаяся группа принудительно завершается. После выхода основного процесса дочитывание pipe ограничено 2 секундами, затем оставшиеся потомки завершаются. Агент ждёт сборщиков и начатые дисковые операции, останавливает HTTP и выполняет финальную попытку отправки; недоставленный spool остаётся на volume.

Возвращается код программы; сигнал даёт `128 + signal`, отсутствующая команда — 127, неисполняемая — 126. Ошибка конфигурации/spool/порта — 1, неправильный CLI — 2. Ошибка сбора после запуска не закрывает pipe и не подменяет код программы.

## Память

Все новые буферы, regex, очереди, echo и реестр файлов покрываются отдельным резервом внутри `LOGNARA_MAX_BUFFER_BYTES`: без источников 512 KiB на диагностику; с источниками `6 MiB + 3 * LOGNARA_MAX_RECORD_BYTES` (12 MiB при стандартном лимите записи). Резерв берётся до запуска сборщиков, остальной бюджет делится между существующими конвейерами. Конфигурация работает с исходным бюджетом 64 MiB.

Очередь каждого сырого потока: 8 блоков по 64 KiB; echo: 64 блока по 4 KiB. Диагностика ограничена такой же очередью. Заблокированный writer удерживает только свой байтовый резерв, а не блокировку spool. Это бюджет объектов, а не точный RSS runtime, HTTP, zstd и allocator.

Проверки профиля с конкурентным HTTP, недоступным relay и последующим восстановлением:

```sh
python3 Lognara-agent/tests/check-memory-profile.py --limit-mib 128
python3 Lognara-agent/tests/check-memory-profile.py --sources --limit-mib 128
```

На macOS arm64/debug измерены пики 86,1 MiB для HTTP и 78,6 MiB с файлами/потоками при пороге 128 MiB; все подтверждённые записи восстановлены. Генератор HTTP работает в измеряемом процессе. Жёсткая квота Linux cgroup и сами контейнерные образы этим профилем не проверяются.

## Подключение приложений

Примеры JSON: [examples/log-sources](../examples/log-sources). Пути в них должны совпадать с настройками приложения и доступными агенту volumes. Готовых Docker-образов с агентом в репозитории нет.

### Nginx

В официальном образе access/error-файлы являются ссылками на stdout/stderr; используйте `run`. [Docker](https://docs.docker.com/engine/logging/)

В своём образе установите подходящий Linux-бинарник агента в `/usr/local/bin/lognara-agent`. Оберните исходный entrypoint, сохранив инициализацию образа:

```yaml
services:
  nginx:
    image: your-registry/nginx-with-lognara:tag
    init: true
    stop_grace_period: 30s
    entrypoint: ["/usr/local/bin/lognara-agent", "run", "--", "/docker-entrypoint.sh"]
    command: ["nginx", "-g", "daemon off;"]
    environment:
      LOGNARA_SERVICE: nginx
      LOGNARA_SERVER: docker-host
      LOGNARA_BACKEND: production
      LOGNARA_RELAY_URL: http://lognara-relay:7401/v1/batches
      LOGNARA_RELAY_TOKEN: ${LOGNARA_RELAY_TOKEN:?Задайте ключ}
    volumes:
      - nginx-agent-spool:/var/lib/lognara-agent/spool
volumes:
  nginx-agent-spool:
```

Для обычных файлов настройте Nginx, например `access_log /var/log/lognara/nginx/access.log;` и `error_log /var/log/lognara/nginx/error.log;`, создайте каталог с нужными правами и используйте [nginx-files.json](../examples/log-sources/nginx-files.json). В обычном режиме отдельно обеспечьте запуск/остановку обоих процессов; режим `run` умеет одновременно читать и файлы.

### PostgreSQL

Для файлов настройте `postgresql.conf`:

```ini
logging_collector = on
log_destination = 'jsonlog'
log_directory = '/var/log/postgresql'
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'
log_truncate_on_rotation = off
```

Collector создаёт JSON-файлы с расширением `.json`; подключите [postgres-json.json](../examples/log-sources/postgres-json.json). Создайте каталог для пользователя postgres; агенту нужны чтение и проход по каталогам. По умолчанию права лог-файлов 0600: агент с тем же UID может их читать, либо используйте выделенную группу и `log_file_mode = 0640` с корректными правами каталогов. JSON-вывод требует `logging_collector`. [PostgreSQL](https://www.postgresql.org/docs/18/runtime-config-logging.html)

Для stderr отключите collector, оставьте `log_destination = 'stderr'` и оберните исходный entrypoint официального образа:

```sh
lognara-agent run -- /usr/local/bin/docker-entrypoint.sh postgres
```

Не заменяйте entrypoint просто запуском `postgres`: образ выполняет инициализацию каталога и смену пользователя. Постоянный spool должен оставаться доступным UID агента; настройка логов и volume не меняет пользователя автоматически.

### Seq

Собственные диагностические JSON-логи Seq находятся в `/data/Logs` в Docker; путь может переопределяться настройками Seq. Используйте [seq-diagnostics.json](../examples/log-sources/seq-diagnostics.json) и доступный агенту каталог. Пример читает только каталог диагностик; записи из внутренней базы Seq этим сборщиком не извлекаются. Формат передаётся как NDJSON без специальной нормализации Seq/CLEF. [Seq](https://datalust.co/docs/stability-troubleshooting)

### MinIO

Для обычного консольного вывода используйте [minio-streams.json](../examples/log-sources/minio-streams.json):

```sh
LOGNARA_SOURCES_FILE=/etc/lognara/minio-streams.json \
  lognara-agent run -- minio server /data
```

Это пример прямого запуска установленного бинарника. В контейнере оборачивайте именно исходный entrypoint вашего образа, как в Nginx; используйте `init: true` и `stop_grace_period: 30s`. Console target включён MinIO постоянно. Audit/webhook-интеграции являются отдельными источниками и не входят в эту реализацию. [MinIO](https://github.com/minio/minio/blob/master/docs/logging/README.md)

Контейнерные примеры проверены по схеме источников и документации; запуск самих образов Nginx/PostgreSQL/Seq/MinIO в локальные проверки не входит. Docker API, journald, syslog, сжатые архивы, CSV, внутренние базы и парсеры полей приложений не поддерживаются.

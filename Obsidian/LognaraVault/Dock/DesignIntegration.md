# Dock: план интеграции дизайнов

Parent: [[Dock/LognaraDock]]

## Статус

План подготовлен по исходникам `db09e16` и шести HTML-шаблонам пользователя; пользователь согласовал полный объём с поэтапной реализацией. Неизменённые эталоны находятся в `docs/design-references/dock/`.

Первый рабочий выпуск реализует общий дизайн, исторический поиск/cursor, связанные логи Trace, отдельный Live, context/ссылки/экспорт загруженных строк и базовую count-аналитику (этапы 0–3A). Фактические контракты описаны в [[Dock/LognaraDock]] и [[Dock/LognaraDock-ProjectMap]]. Этап 3B добавляет общий summary с текстовым подсчётом/stacked histogram и первой страницей, приблизительный p95/покрытие и action-группы. Этап 4 добавляет серверные паттерны сообщений: детерминированный pattern_id, фоновый каталог core, режим `/logs?view=patterns` и персональное скрытие в dock ([контракт](../../../docs/DockPatternsContract.md)). Проблемы, телеметрия, алерты и полноценные spans остаются дальнейшими этапами плана.

- [Полный план](../../../docs/DockDesignIntegrationPlan.md): страницы, визуальные токены, поведение, этапы, зависимости, проверки и открытые вопросы.
- [Исследование API](../../../docs/DockDesignApiResearch.md): возможности текущих core/dock и недостающие контракты.

## Соответствие шаблонов

| Шаблон | Назначение |
|---|---|
| Main.dc.html | События на странице логов. |
| variant-f.dc.html | Паттерны на той же странице логов. |
| analytics.dc.html | Аналитика. |
| errors.dc.html | Проблемы, объединяющие повторяющиеся ошибки. |
| infra.dc.html | Цепочка доставки, узлы и хранилище. |
| alerts.dc.html | Редактор правил и история срабатываний. |

Вход, аккаунт и существующие подключения сохраняются и используют общий визуальный слой. Шаблоны статические; их support/vendor runtime не является частью текущего dock.

## Основные зависимости

Первый предложенный выпуск: общий дизайн → исторический поиск и корреляция trace → базовая аналитика. Count/text-aware histogram/percentiles реализованы единым summary core; [wire-контракт](../../../docs/DockSummaryContract.md). Паттерны требуют серверного конвейера и стабильной идентичности; проблемы добавляют persistent lifecycle. Мониторинг узлов требует идентичности и heartbeat agent → relay → core. Алерты требуют фонового evaluator и долговечной доставки в dock.

Текущий SSE ограничен окном/размером и не является полным источником агрегатов или алертов. Реестр подключений пока не связан с source-полями событий. Текущий trace API возвращает логи; длительности spans из него не следуют.

Решения пользователя: полный план с поэтапной реализацией; Trace сначала показывает связанные логи, полноценные spans реализуются отдельным этапом; первые каналы алертов — Telegram и Discord. Детали контрактов и граница первого выпуска остаются предложениями плана.

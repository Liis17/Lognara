# Метрики из логов

Parent: [[Index]]

**Статус:** проектное решение принято 2026-10-13, не реализовано. Сейчас core хранит `attributes` одной JSON-строкой и считает только количество событий (гистограмма и группировка), см. [[Core/LognaraCore]].

## Цель

Приложения отдают метрики через логи. Core извлекает их в отдельное хранилище и хранит всю историю, чтобы рисовать графики за любой период. Внешние системы не используются.

## Два источника метрик

| Источник | Как распознаётся | Стоимость |
|----------|------------------|-----------|
| Встроенный формат Lognara | Core видит объект метрик в событии. Проверка всегда включена. | Проверка наличия поля. |
| Правила с регулярным выражением | Задаются вручную в dock и включаются только для выбранных источников. Без правил события идут как обычные логи. | Сравнение source, затем обязательная подстрока, затем regex. |

Строка с метрикой всегда сохраняется и как лог. Это нужно для пересчёта истории после исправления правила и для отладки. Мешающие строки скрываются фильтром в интерфейсе, а не удаляются.

## Встроенный формат

Формат повторяет то, что уже пишут сервисы BarkFluff (`BarkFluff.GrpcServer.Metrics.MetricsReporterService`), чтобы им не пришлось ничего менять:

```json
{"SchemaVersion":2,"ServiceName":"BarkFluff.Onliner","Counters":{"offline_detection_runs":10},"Gauges":{},"Timestamp":"2026-10-13T15:14:00.4480321Z"}
```

- Событие приходит раз в ~10 секунд от каждого экземпляра сервиса, с сообщением `ServiceMetrics {json}`. Тот же объект лежит в свойстве `Metrics`. Другие свойства: `Application`, `EnvironmentName`, `MachineName` (ID контейнера).
- `Counters` — приращения с прошлого отчёта, нулевые значения опускаются. Агрегация: сумма. Сброс после рестарта обрабатывать не нужно.
- `Gauges` — текущее значение. Агрегация: последнее, min, max, avg.
- Время точки берётся из `Timestamp` (UTC), а не из времени строки лога.
- Незнакомая `SchemaVersion` не разбирается и учитывается в счётчике ошибок разбора.
- Ряды по умолчанию суммируются по всем `MachineName` сервиса: ID контейнера меняется при каждом деплое.

## Правила с регулярным выражением

Для сервисов, которые не поддерживают встроенный формат. Выполняются в core при материализации, а не в агенте: правила хранятся в одном месте и могут пересчитать историю.

| Поле | Назначение |
|------|------------|
| Область | `service` обязательно; `environment`, `server`, `backend` по желанию. Не агент: `service_instance` меняется при пересоздании контейнера. |
| Обязательная подстрока | Дешёвая проверка до запуска regex. |
| Регулярное выражение | Крейт `regex` (линейное время), именованные группы. Лимит размера выражения и числа правил. |
| Имя метрики | Постоянное или из группы. |
| Тип | counter или gauge. Без группы `value` правило считает совпадения (+1). |
| Метки | Только явно выбранные группы. Лимит рядов на правило против высокой кардинальности. |

Перед сохранением dock показывает предпросмотр: правило прогоняется по последним логам выбранного сервиса, видны совпавшие строки и полученные точки. Изменённое правило действует на новые события, старые пересчитываются только явным запуском пересчёта.

## Хранение

- Отдельное хранилище `metrics/` в Parquet: время, сервис, окружение, машина, имя метрики, тип, метки, значение.
- Ключ против дубликатов доставки: `(ServiceName, MachineName, Timestamp)` для встроенного формата, ID исходного события для правил. Без него повторная доставка удвоит приращения.
- Свёртки 1 минута, 1 час, 1 день: `count`, `sum`, `min`, `max`. Если появятся перцентили, к ним добавится скетч (DDSketch).
- Удаления нет. Оценка для 20 сервисов по 10 счётчиков с отчётом раз в 10 секунд: около 630 млн точек в год, единицы GiB в колоночном виде. Холодное хранилище из [[Design/LongTermStorage]] для метрик не обязательно.

## API и права

- `POST /v1/metrics/series`: метрика, область, интервал времени, шаг. Шаг выбирает сырые точки или свёртку.
- Управление правилами и предпросмотр требуют отдельного admin-токена core. Query-токен dock даёт только чтение.
- Dock получает графики, редактор правил с предпросмотром и запуск пересчёта истории.

## Порядок работ

1. Хранилище метрик, встроенный формат, дедупликация.
2. API графиков и графики в dock.
3. Правила с регулярным выражением: API в core, редактор с предпросмотром в dock.
4. Пересчёт истории из сохранённых логов.

Метрики не зависят от compaction из [[Design/LongTermStorage]] и идут первыми.

## Открытый вопрос: доставка логов BarkFluff

Сейчас BarkFluff пишет логи только в Seq, в формате Serilog, консольный вывод выключен. Сбора консоли в агенте нет, агент принимает только `POST /v1/logs`. Варианты:

- Включить в Serilog консольный вывод в JSON и добавить в агент сбор консоли.
- Отправлять логи HTTP-sink'ом Serilog прямо в `POST /v1/logs` агента.
- Добавить в агент приём, совместимый с Seq (CLEF), чтобы BarkFluff сменил только адрес Seq. Тогда relay должен разбирать ключи CLEF (`@t`, `@mt`/`@m`, `@l`), сейчас он знает только `timestamp`, `message`, `level`.

От выбора зависит, где core находит объект метрик: в `attributes.Metrics` или в тексте сообщения.

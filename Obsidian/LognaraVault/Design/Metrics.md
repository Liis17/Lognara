# Метрики из логов

Parent: [[Index]]

**Статус:** реализовано 2026-10-14 в core и dock, кроме свёрток и пересчёта истории. Проектное решение принято 2026-10-13. Отличия реализации от проекта перечислены в разделе «Отличия реализации». Устройство кода: [[Core/LognaraCore]], [[Dock/LognaraDock]].

## Цель

Приложения отдают метрики через логи. Core извлекает их в отдельное хранилище и хранит всю историю, чтобы рисовать графики за любой период. Внешние системы не используются.

## Два источника метрик

| Источник | Как распознаётся | Стоимость |
|----------|------------------|-----------|
| Встроенный формат Lognara | Core видит объект метрик в событии. Проверка всегда включена. | Проверка наличия поля. |
| Правила с регулярным выражением | Задаются вручную в dock и включаются только для выбранных источников. Без правил события идут как обычные логи. | Сравнение source, затем обязательная подстрока, затем regex. |

Строка с метрикой всегда сохраняется и как лог. Это нужно для пересчёта истории после исправления правила и для отладки. Мешающие строки скрываются фильтром в интерфейсе, а не удаляются.

## Встроенный формат

Формат повторяет то, что уже пишут сервисы BarkFluff (`BarkFluff.GrpcServer.Metrics.MetricsReporterService`), чтобы им не пришлось ничего менять:

```json
{"SchemaVersion":2,"ServiceName":"BarkFluff.Onliner","Counters":{"offline_detection_runs":10},"Gauges":{},"Timestamp":"2026-10-13T15:14:00.4480321Z"}
```

- Событие приходит раз в ~10 секунд от каждого экземпляра сервиса, с сообщением `ServiceMetrics {json}`. Тот же объект лежит в свойстве `Metrics`. Другие свойства: `Application`, `EnvironmentName`, `MachineName` (ID контейнера).
- `Counters` — приращения с прошлого отчёта, нулевые значения опускаются. Агрегация: сумма. Сброс после рестарта обрабатывать не нужно.
- `Gauges` — текущее значение. Агрегация: последнее, min, max, avg.
- Время точки берётся из `Timestamp` (UTC), а не из времени строки лога.
- Незнакомая `SchemaVersion` не разбирается и учитывается в счётчике ошибок разбора.
- Ряды по умолчанию суммируются по всем `MachineName` сервиса: ID контейнера меняется при каждом деплое.

## Правила с регулярным выражением

Для сервисов, которые не поддерживают встроенный формат. Выполняются в core при материализации, а не в агенте: правила хранятся в одном месте и могут пересчитать историю.

| Поле | Назначение |
|------|------------|
| Область | `service` обязательно; `environment`, `server`, `backend` по желанию. Не агент: `service_instance` меняется при пересоздании контейнера. |
| Обязательная подстрока | Дешёвая проверка до запуска regex. |
| Регулярное выражение | Крейт `regex` (линейное время), именованные группы. Лимит размера выражения и числа правил. |
| Имя метрики | Постоянное или из группы. |
| Тип | counter или gauge. Без группы `value` правило считает совпадения (+1). |
| Метки | Только явно выбранные группы. Лимит рядов на правило против высокой кардинальности. |

Перед сохранением dock показывает предпросмотр: правило прогоняется по последним логам выбранного сервиса, видны совпавшие строки и полученные точки. Изменённое правило действует на новые события, старые пересчитываются только явным запуском пересчёта.

## Хранение

- Отдельное хранилище `metrics/` в Parquet: время, сервис, окружение, машина, имя метрики, тип, метки, значение.
- Ключ против дубликатов доставки: `(ServiceName, MachineName, Timestamp)` для встроенного формата, ID исходного события для правил. Без него повторная доставка удвоит приращения.
- Свёртки 1 минута, 1 час, 1 день: `count`, `sum`, `min`, `max`. Если появятся перцентили, к ним добавится скетч (DDSketch).
- Удаления нет. Оценка для 20 сервисов по 10 счётчиков с отчётом раз в 10 секунд: около 630 млн точек в год, единицы GiB в колоночном виде. Холодное хранилище из [[Design/LongTermStorage]] для метрик не обязательно.

## API и права

- `POST /v1/metrics/series`: метрика, область, интервал времени, шаг. Шаг выбирает сырые точки или свёртку.
- Управление правилами и предпросмотр требуют отдельного admin-токена core. Query-токен dock даёт только чтение.
- Dock получает графики, редактор правил с предпросмотром и запуск пересчёта истории.

## Порядок работ

1. Хранилище метрик, встроенный формат, дедупликация. Реализовано, дедупликация с ограничениями (см. отличия).
2. API графиков и графики в dock. Реализовано.
3. Правила с регулярным выражением: API в core, редактор с предпросмотром в dock. Реализовано.
4. Пересчёт истории из сохранённых логов. Не реализовано.

Метрики не зависят от compaction из [[Design/LongTermStorage]] и идут первыми.

## Отличия реализации

Состояние на 2026-10-14, проверено по `Lognara-core/src`, `Lognara-dock/src`, тестам и `Lognara-core/examples/series_bench.rs`.

**Маршруты и запрос**

- Вместо `POST /v1/metrics/series` реализованы `GET /v1/series` (список) и `POST /v1/series/query` (значения). Запрос принимает `service`, `name`, `from`, `to`, `step_seconds`, `split` (`none`, `instance`, `labels`) и `origin`.
- Фильтров по окружению, серверу и бэкенду в запросе нет: при `split: none` сумма идёт по всем окружениям и экземплярам.
- Свёрток (минута, час, сутки) нет. Каждый график считается по сырым точкам, `step_seconds` от 1 до 604800, корзин не больше 10000.
- Серий в ответе не больше 20. Лишние отбрасываются по сумме модулей значений в окне, признака обрезки в ответе нет.
- Пересчёта истории нет: ни маршрута, ни кода. Правило действует только на строки, материализованные после изменения.

**Встроенный формат**

- Core читает только `attributes.Metrics`. Текст сообщения `ServiceMetrics {json}` не разбирается.
- Колонки серий: время, `service`, `environment`, `server`, `backend`, `service_instance`, `name`, `origin`, `rule_id`, `labels`, `value`, `event_id`. Поля `MachineName` и `ServiceName` из отчёта не читаются: сервис и экземпляр берутся из источника агента.
- Ключ дедупликации в запросе: строки с одинаковыми источником, `name`, `origin`, `rule_id`, `labels`, `timestamp` и `event_id` сворачиваются через максимум значения. Для встроенных точек `event_id` пуст, поэтому повтор того же отчёта от того же источника учитывается один раз. Тест `duplicate_deliveries_of_one_report_are_counted_once` покрывает только этот случай.
- Точки правил имеют `event_id`, поэтому повтор с новым id даёт двойной счёт. Для правил теста нет.
- Значения по умолчанию: `Counters` (`delta`) - сумма, `Gauges` - среднее. Тип `cumulative` считает приращения между корзинами, уменьшение счётчика принимается как перезапуск.

**Метки и правила**

- Метки хранятся канонической строкой `k=v,k2=v2` по возрастанию ключа, без экранирования запятых и знаков равенства. Значение обрезается до 128 байт по границе UTF-8. Группы, не участвовавшие в совпадении, опускаются.
- Правило задаёт `environment`, `contains`, `pattern`, `value_group` и `label_groups`. Фильтров `server` и `backend` у правила нет, как и группы для имени метрики: имя фиксировано определением.
- Типы определения: `delta`, `cumulative`, `gauge`. Проектные `counter` и `gauge` соответствуют `delta` и `gauge`.
- Лимит меток: 1000 различных наборов меток на правило, состояние в памяти процесса. После рестарта счёт начинается заново. Отброшенные точки считаются в `lognara_core_series_dropped_points_total`.
- Коллизия имени правила с native-метрикой (тот же `service` и `name`) проверяется только при записи определения (`create` и `update`). Если native-метрика появится позже, проверки нет.
- Предпросмотр сканирует не больше 5000 последних строк сервиса (с учётом `environment`, подстрока через LIKE), окно 1-60 минут, в dock всегда 60. Показывает до 50 образцов.
- Лимиты правил: до 64 правил с `rule` на хранилище, `contains` 1-256 байт, `pattern` до 4096 байт, размер regex 1 MiB, до 4 групп меток.

**Хранение и производительность**

- Файлы `metrics/YYYY/MM/DD/<id>.parquet` по одному на закрытый сегмент, слияние одного дня за проход. Удаления нет, retention эти файлы не трогает.
- Бенчмарк `series_bench` (release, macOS, 3 сервиса по 3 счётчика, 2 экземпляра, точка каждые 10 секунд, 365 дней): 56 764 800 точек, 365 файлов, 27,1 MiB в `metrics/`. Год с шагом 1 день: 15,2-15,9 секунды. 30 дней с шагом 1 час: около 0,36 секунды. 24 часа с шагом 1 минута: около 12 миллисекунд. Год с `split: instance`: 15,4-16,1 секунды. Годовые графики медленные: свёрток нет.
- Dock выбирает шаг сам: самый мелкий из списка, при котором не больше 1000 корзин. Для года это 12 часов (730 корзин). Такой шаг не измерялся, измерен только шаг 1 день.
- Лимит аналитики общий со статистикой: два одновременных запроса, таймаут 30 секунд.

**Dock**

- Фильтра, скрывающего строки метрик в ленте логов, нет: в коде dock нет упоминаний `ServiceMetrics`.
- Редактор правил и предпросмотр доступны только при заданном `LOGNARA_DOCK_CORE_ADMIN_TOKEN` (`series_admin` в `/api/me`).

## Открытый вопрос: доставка логов BarkFluff

Сейчас BarkFluff пишет логи только в Seq, в формате Serilog, консольный вывод выключен. Сбора консоли в агенте нет, агент принимает только `POST /v1/logs`. Варианты:

- Включить в Serilog консольный вывод в JSON и добавить в агент сбор консоли.
- Отправлять логи HTTP-sink'ом Serilog прямо в `POST /v1/logs` агента.
- Добавить в агент приём, совместимый с Seq (CLEF), чтобы BarkFluff сменил только адрес Seq. Тогда relay должен разбирать ключи CLEF (`@t`, `@mt`/`@m`, `@l`), сейчас он знает только `timestamp`, `message`, `level`.

От выбора зависит, где core находит объект метрик: в `attributes.Metrics` или в тексте сообщения.

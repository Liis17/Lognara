# Собственные логи Lognara

Parent: [[Architecture]]

## Сбор и управление

`Lognara-selflog/` подключает дополнительный tracing Layer к бинарникам core, dock и relay. Консольный вывод сохраняется. Собираются события с target `lognara_*`, разрешённые текущим `RUST_LOG` (по умолчанию info). События зависимостей, включая Tantivy, не собираются: запись логов сама запускает работу индекса.

Сервисы в поиске: `lognara-core`, `lognara-dock`, `lognara-relay`; backend `lognara`, environment отсутствует. Server и service_instance берутся из HOSTNAME, затем COMPUTERNAME, затем имени сервиса. Для стабильной группировки контейнеров задавайте стабильный hostname. Сообщение и уровень сохраняются отдельно; target и структурированные поля находятся в `attributes.selflog`.

В Dock «Настройки → Собственные логи Lognara» управляют тремя глобальными переключателями (все экземпляры соответствующего компонента). По умолчанию все включены. Управление доступно авторизованным пользователям, как остальные операции управления инфраструктурой. Core атомарно сохраняет настройки в `self-logs.json` внутри data_dir. Повреждённый или нечитаемый self-logs.json не блокирует запуск core: используются значения по умолчанию с предупреждением, файл сохраняется до явного изменения настроек. Изменения опрашиваются каждые 10 секунд; при недоступности core действует последнее значение, кешированное рядом с очередью. На первом запуске без кеша сбор включён. Отключение прекращает новый сбор, но не удаляет историю и не препятствует доставке уже сохранённой очереди. Повторное включение возобновляет сбор.

## Доставка и ограничения

Layer использует неблокирующий канал на 256 событий. Worker отдельного std-потока пишет через [[Delivery/Spool]] в `self-log-spool` внутри data_dir core/dock и spool_dir relay. Квоты на процесс: 32 MiB, 100000 событий, 4096 частей. При переполнении канала/дисковой очереди или ошибке записи новые события теряются, счётчик потерь выводится в stderr. До записи worker в spool события находятся в памяти и могут потеряться при аварийном завершении. Ограничены размер сообщения (8 KiB), суммарный текст дополнительных полей (8 KiB) и их количество (24).

Запрос содержит до 16 событий и 256 KiB JSON; большие группы делятся по фактическому размеру сериализации. Worker повторяет сохранённые байты с паузой 5 секунд при отказе; успешно принятые части удаляются только после durable ACK. При ответах 400/413 часть сначала атомарно сохраняется в rejected рядом с основной очередью, затем основная очередь продвигается. Архив ограничен 8 MiB и 4096 частями; при заполнении старые записи не удаляются, основная очередь сохраняет отклонённую часть и повторяет попытку. Ошибка чтения spool сохраняет исходные файлы и вызывает повторное открытие; повреждённый или нечитаемый файл может потребовать ручного восстановления. При ошибке ACK очередь повторно открывается с диска; захват продолжает работать, но при недоступности диска новые события могут теряться. Остановка сохраняет остаток канала на диск, без обязательной финальной сетевой доставки. Сетевые запросы выполняет отдельный поток с одним запросом в работе; их ожидание не блокирует сброс канала в spool. HTTP timeout 3 секунды, redirect отключён. При аварийном завершении потока отправки worker сообщает об этом в stderr и продолжает сохранять новые сообщения в пределах квоты; доставка возобновляется после перезапуска процесса. Собственные транспортные операции обоих потоков выполняются с NoSubscriber и не порождают новые собираемые события.

Core передаёт собственные записи напрямую в `Journal::accept` вне async executor. Dock отправляет в `POST /v1/admin/self-logs` с существующим admin-токеном, relay в `POST /v1/self-logs` с персональным relay-токеном. У relay LOGNARA_CORE_URL содержит полный endpoint /v1/batches, поэтому self-logs и self-logs/settings строятся как соседние пути (как heartbeat и agents). Авторизация выполняется до чтения тела; query-токен для записи не подходит. Endpoint relay разрешает только service lognara-relay, endpoint dock только lognara-dock. Удаление relay отзывает и этот доступ. Формирование событий и запись находятся в `Lognara-core/src/self_logs.rs`, HTTP-обработчики только проверяют границу и вызывают модуль.

Core преобразует JSON в стабильный MessagePack + zstd: UUID и timestamp заданы при захвате; ingested_at равен timestamp, attributes имеет единственную карту selflog. Повторы дают одинаковый SHA-256 и используют существующую дедупликацию WAL. ACK 204 выдаётся после `Journal::accept`, который сохраняет прежние fsync, квоты и ingest admission. Обычные поиск, паттерны, retention и аналитика работают без нового формата сохранённых событий.

Настройки: GET/PUT `/v1/admin/self-logs/settings` (admin), GET `/v1/self-logs/settings` (relay). Dock проксирует GET/PUT `/api/settings/self-logs` с проверкой сессии и Origin; серверные токены не передаются в браузер. При обновлении сначала поставляется core, затем dock/relay; старый core не знает новых endpoints, поэтому новые отправители до его обновления накапливают очередь в пределах квоты.

Исходники: `Lognara-selflog/src/lib.rs`, `Lognara-core/src/self_logs.rs`, точки входа `src/main.rs` трёх сервисов, `Lognara-dock/src/self_logs.rs`, `Lognara-dock/web/src/pages/Settings.tsx`. Проверки: unit-тесты selflog (захват, пределы, отключение, разбиение), HTTP-тест фактических путей relay, токена и кодов отказа; Unix-тесты очереди при отказе/перезапуске, подавления рекурсии и записи на диск при зависшей сети; `Lognara-core/tests/self_logs.rs` (авторизация, ACK, дедупликация, поиск и сохранение настроек); `Lognara-dock/web/tests/self-logs.spec.ts` (настройки и отказ сохранения).

`Lognara-core/tests/self_logs_startup.rs`, `Lognara-dock/tests/self_logs_startup.rs` и `Lognara-relay/tests/self_logs_startup.rs` проверяют сохранение фатального сообщения при ошибке инициализации и занятом порте до выхода бинарника.

Суммарный постоянный бюджет на процесс: основная очередь 32 MiB и архив отклонённых частей 8 MiB, без учёта небольших служебных файлов и временной копии атомарной записи. Архив не участвует в поиске и сохраняется для диагностики постоянных отказов.

При отказе до запуска worker (например, ошибка конфигурации или открытия хранилища core) автоматической доставки нет: диагностика остаётся в консоли. Ошибки HTTP после старта worker сохраняются перед выходом процесса.

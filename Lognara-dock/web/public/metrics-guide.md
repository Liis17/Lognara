# Наборы метрик Lognara

Подготовь JSON для импорта в Dock по реальным сообщениям логов проекта. Формат: `lognara-metrics`, версия `1`. Сервер и сервис пользователь выбирает в Dock; в JSON их указывать нельзя.

```json
{
  "format": "lognara-metrics",
  "version": 1,
  "metrics": [{
    "name": "requests.completed",
    "title": "Завершённые запросы",
    "description": "Количество завершений по HTTP-статусу",
    "unit": "запросов",
    "kind": "delta",
    "aggregation": "sum",
    "enabled": true,
    "rule": {
      "environment": null,
      "contains": "request completed",
      "pattern": "request completed status=(?P<status>[1-5]\\d{2})",
      "value_group": null,
      "label_groups": ["status"]
    }
  }]
}
```

Схема: `/metrics-schema.json`. Готовый пример: `/metrics-example.json`. Набор nginx: `/metrics-nginx.json`.

## Инструкция для агента

1. Изучи фактический формат вывода логов, их сериализацию и сообщения. Не придумывай поля и сообщения, которых приложение не пишет. Правило работает с текстом `message`, а не со всем JSON события.
2. Создай от 1 до 64 метрик с уникальными `name` (1–128 ASCII-символов: буквы, цифры, `_ . : -`). Добавь понятные заголовки, описание смысла и единицы. Заголовок до 128 символов, описание до 2000, единица до 32.
3. `delta` означает приращение, обычно с `sum`. Без `value_group` каждое совпадение даёт +1. Для размеров и других приращений извлекай числовую именованную группу.
4. `gauge` означает текущее измерение, обычно с `avg`; доступны `sum`, `avg`, `min`, `max`, `last`. `cumulative` используется только для накопительного значения счётчика; запрос вычисляет сумму приращений с учётом сбросов. Это не способ подсчёта отдельных событий.
5. Используй синтаксис Rust `regex`: именованные группы `(?P<name>...)`, без lookaround и обратных ссылок. `pattern` до 4096 байт, размер скомпилированного regex ограничен 1 MiB. В JSON обратную косую нужно удваивать: regex `\d+` записывается как `"\\d+"`.
6. `contains` обязателен: непустая буквальная подстрока от 1 до 256 байт для дешёвого отбора. Она должна встречаться во всех подходящих сообщениях. `value_group` — имя числовой группы или `null`; принимаются только конечные числа.
7. `label_groups` содержит до четырёх разных имён групп из regex. Не включай IP, URL, ID запросов и другие неограниченные значения: максимум 1000 наборов меток на правило за время жизни процесса. Предпочитай статус, класс результата или небольшой перечень действий.
8. `environment` — точное окружение или `null` для всех. Если окружение неизвестно, используй `null`.
9. Отдельно перечисли реальные примеры сообщений для проверки и объясни ограничения покрытия. Сам импортируемый JSON должен соответствовать схеме и не содержать дополнительных полей.

Неизвестные поля отклоняются. Ограничения размеров строк Core проверяет в байтах там, где это указано; JSON Schema дополняет, но не заменяет серверную проверку. На всё хранилище действует лимит 64 определения с правилами, включая отключённые.

## Применение

В Dock выбери сервер, затем сервис, вставь JSON и нажми «Проверить набор». Для существующих имён выбери «Пропустить», «Переименовать» или «Заменить». Замена сохраняет ID определения. Проверка логов сканирует до 5000 последних подходящих строк за 60 минут; отсутствие совпадений не запрещает создание.

Весь выбранный набор сохраняется атомарно. Если определения изменились после проверки, повтори проверку. Новые и изменённые правила применяются к новым материализуемым логам; пересчёта истории нет. Существующие точки при изменении или удалении определения сохраняются.

Шаблоны nginx рассчитаны на текст стандартного `combined` access-лога и стандартного error-лога. Метрики: запросы, запросы по статусу, 4xx, 5xx, `body_bytes_sent`, записи по severity. Поле времени ответа в стандартном combined отсутствует. Сбор логов nginx должен быть настроен отдельно.

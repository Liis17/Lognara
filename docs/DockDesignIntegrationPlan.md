Критические различия с примерами:

- В API уровни записаны `error`, `warn` и т. д.; в интерфейсе допустимы `ERROR`, `WARN`. Поле инстанса — `service_instance`.
- `duration_ms` не является верхнеуровневым полем события. Summary читает числовой конечный неотрицательный attributes.duration_ms и считает приблизительный p95 t-digest с покрытием; браузерная выборка не используется.
- SearchResponse содержит `events`, `next_cursor`, `as_of`, но не `total`. Summary возвращает точный total вместе с первой страницей; длина загруженной страницы не используется как общий подсчёт.
- Старые histogram/group-by не принимают `text` и не группируют произвольные `attributes`; summary поддерживает text и duration_ms. Group-by возвращает ограниченный top count; это не полный список сервисов или универсальные facets.
- Каждая summary удерживает один снимок для total, таблицы и диаграммы. Предыдущее окно и каталог сервисов — отдельные запросы; у них нет общего watermark с текущим окном.
- SSE сейчас опрашивает последние события с limit=1000, даёт начальный снимок до 200 и хранит в браузере 2000. Это лента последних событий с возможными пропусками, не источник полного подсчёта и алертов.
- `ingested_at` выставляет агент. Внутренний `core_received_at` пока не выдаётся в LogEvent; разность текущих полей не равна задержке до core.
- Источник события не содержит id зарегистрированного relay/агента. Статус нельзя выводить из совпадения имени сервиса с именем профиля.
- Retention сырых событий по умолчанию 7 дней, а шаблон алерта предполагает 30 дней истории паттернов. Этот baseline требует отдельного долговечного состояния либо изменения политики retention.

## Этапы и критерии завершения

### 0. Зафиксировать входные контракты

Сохранить копии шести эталонов и provenance в репозитории до реализации; оригиналы пользователя не изменять. Зафиксировать решения из таблицы вопросов, подмножество языка поиска, семантику ERROR/FATAL, duration, fingerprint и идентичности узла. На каждом этапе детализировать только его контракты; остальные предложения сохранять в backlog.

Проверка: эталоны доступны из ветки; разработчик отличает подтверждённый API от будущего; вопросы, влияющие на следующий этап, закрыты.

### 1. Оформление и существующие функции dock

Изменить `web/src/index.css`, `App.tsx`, существующие страницы, добавить общие UI-компоненты и локальные fonts. Перенести форму shell и табличный режим событий без переписывания авторизации. Оформить `/access`, `/settings`, `/login` по общей системе. Закрепить empty/loading/error/unauthorized состояния; выделить верхнюю панель и область данных.

Проверка: вход паролем/passkey, выход, смена пароля, добавление/удаление passkey, создание/удаление relay/agent, одноразовый токен, SSE и пауза работают как раньше. Эталоны и реальные экраны сравнены в браузере, web build и затронутые dock-тесты проходят.

### 2. Исторический поиск, логи и Trace по связанным событиям

- Расширить `CoreClient` типизированным поиском с filters/text/cursor и полным ответом; сохранить удобный метод получения последних событий для Live. Добавить в dock `POST /api/logs/search` и `GET /api/traces/{trace_id}`.
- Переводить строку `service:billing AND level:(ERROR OR WARN)` в типизированный запрос. Первая грамматика: точные поля, AND между полями, OR внутри значений одного поля, текст all/phrase. Ошибку и неподдерживаемую конструкцию показывать явно. Произвольный boolean DSL требует нового core-контракта; SQL не добавлять.
- Хранить зафиксированные from/to во время пагинации, обрабатывать 410 с перезапуском поиска; отменять устаревшие запросы при смене фильтров. Limit в UI начать с 50.
- Сохранять серверный порядок истории: timestamp имеет наносекундную точность, JS Date теряет её, внутренний sequence сейчас не выдаётся. Live-фильтрация общего потока не обеспечивает полноту конкретного сервиса: его события могут не попасть в глобальные top1000. Для полной фильтрованной ленты требуется публикационный tail с gaps/resume/backfill.
- Разделить историю и live. Live фильтрует входящие события по поддерживаемым условиям; изменение запроса инициирует новый поиск. Пауза не теряет ограниченный накопленный буфер, переподключение не дублирует строки. Событие `lagged` и достижение лимита показывают необходимость обновления истории.
- Context ±5 мин открывает поиск по timestamp и источнику события; trace использует trace_id. Нет trace_id — действие недоступно с объяснением. Это связанные логи, без придуманных длительностей spans.
- Реализовать копирование ссылки и экспорт JSON/CSV. Первый экспорт — явно обозначенные загруженные события. Полный экспорт — отдельный серверный поток/задача с ограничениями диапазона, объёма, времени и обработкой истёкшего snapshot; его готовность нужна перед обещанием «все результаты».

Проверка: запрос из шаблона эквивалентен ручным фильтрам core; разные уровни/инстансы корректны; cursor не повторяет/не пропускает строки; 400/401/410/503/timeout отображаются; context и ссылки восстанавливают диапазон; trace пагинируется; JSON/CSV сохраняет значения и границы экспорта.

### 3A. Базовая аналитика на текущем core — граница первого выпуска

Добавить dock proxy `POST /api/stats/histogram`, `POST /api/stats/group-by`; в UI — страницу `/analytics`, выбор периода/сервиса, total по сумме histogram, среднюю скорость за выбранное окно, долю ERROR, распределение уровней и top сервисов по ERROR. Сравнение — предыдущее окно той же длины; нулевая база отображается без деления на ноль.

Выбирать interval по диапазону, максимум 86400 секунд; при превышении 10000 buckets сохранять поиск/cursor без сводки с объяснением; UTC floor в core отличать от часового пояса подписей. Источник метрики «событий в минуту» подписать как среднее за окно. Отдельные ответы могут иметь разные `as_of`, до 3B не обещать один атомарный снимок всей страницы.

На странице событий histogram и total подключать для запросов, которые текущая аналитика может выразить. Для текстового запроса временно показывать количество загруженных строк и явно объяснять недоступность общего подсчёта/диаграммы. Не показывать глобальный график как результат текстового фильтра. Готовность этой части не означает полную готовность `Main.dc.html`.

Текущий histogram не выдаёт серии по level. Можно ограниченно запрашивать нужные уровни последовательно, но не создавать fan-out на каждую карточку/уровень: core имеет 2 analytics slots, dock query timeout 35 s при default core timeout 30 s (Live/admin остаются 10 s). Согласовать отдельные timeout аналитики, cancellation и максимальное число запросов. Полный согласованный stacked graph относится к 3B.

Проверка: число событий/доля/сравнение совпадают с серверными данными, пустой период и null-поля отображаются, top-N не представлен как полный каталог сервисов, нагрузка страницы укладывается в query slots. Переключение графика/карточки ведёт к эквивалентному фильтру логов.

### 3B. Полная аналитика и точные показатели шаблонов

Реализовано единым summary, включая первую страницу в одном Snapshot. Метод p95 — приблизительный t-digest; duration читается из существующего JSON без миграции. Лимиты и точный контракт зафиксированы в [DockSummaryContract.md](DockSummaryContract.md). KPI паттернов остаётся этапом 4.

Расширить core типизированными API: count с теми же filters/text, histogram по level за один снимок, согласованный summary, percentiles числового `attributes.duration_ms` и статистика duration по action. Не вводить внешний SQL endpoint. Для text-aware histogram нужен общий механизм совпадения с поиском, а не независимый парсер.

Зафиксировать duration в миллисекундах: учитываются только валидные конечные неотрицательные числа; отсутствие означает «нет измерения». Выбрать exact/approx p95 и сообщать метод; response включает число измеренных событий и долю покрытия. Для старых данных определить чтение/backfill атрибута; для производительности при необходимости материализовать отдельную числовую колонку с версионированием схемы.

Колонка «Вызовов» требует определения события завершения операции или distinct request/span. Текущий group-by action считает лог-события, а одна операция может создавать несколько строк; до появления такого контракта подписывать число как «Событий».

Проверка: total/histogram/table используют одинаковые условия и согласованный watermark, p95 проверяется известной числовой выборкой, нет измерений → пустое состояние, unknown/debug/fatal/trace не исчезают из знаменателя. KPI паттернов добавляется после этапа 4. «ERROR» и «ошибки ERROR+FATAL» не смешиваются без принятого определения.

### 4. Паттерны сообщений как серверные данные

Ввести версионированный deterministic pattern_id и серверный конвейер формирования паттернов. Предложение: обработка и агрегаты в core рядом с источником событий; персональное скрытие — dock SQLite. Не группировать всю историю в браузере и не нормализовать произвольные слова как `word` без правил.

Согласовать распознавание чисел/IP/UUID и других переменных, сохранение значимых констант, границы environment/service/level, обработку многострочных сообщений. Одинаковое сообщение при одинаковой версии алгоритма имеет стабильный id. Не менять идентичность при каждом пользовательском поиске.

Нужны: список/сортировка, count/share, histogram/sparkline, предыдущее окно/growth, first_seen, new status, распределение значений переменных и ограниченные примеры. Доля имеет явный знаменатель; «новый» относится к истории заданной области, а не к первой строке текущей страницы. Рост при нулевой базе обозначается «новый». Для перехода «все события» поиск должен принимать pattern_id и cursor.

Получать новые публикации через серверный cursor по sequence/watermark с восстановлением checkpoint; разработать этот контракт в core, сейчас его нет. Ограничить память/кардинальность, хранить границы обработанного диапазона, определить retention/rebuild/version migration. Выборка примеров не может служить источником count.

Проверка: переменные отделяются от значимого текста, разные ошибки не сливаются, id стабильны после рестарта, count не меняется от размера страницы, rebuild не создаёт двойной учёт, поздние события и retention обрабатываются определённым способом. Все действия строки паттерна ведут к работающим разделам после их этапов.

### 5. Ошибки как проблемы с жизненным циклом

Использовать pattern-механизм, но определить отдельный fingerprint ошибки: область environment/service/action + тип exception/значимые application frames, fallback к паттерну сообщения. Stack trace читать из согласованных attributes; отсутствие stack/deploy metadata не заменять примером из HTML.

Core предоставляет группировку, count, уникальные servers, first/last_seen, примеры и динамику. Dock SQLite хранит статус, отметку решения, историю действий и связь с fingerprint; серверный worker отслеживает новые случаи. Добавить API списка/деталей/resolve/reopen и ссылки «все события», «алерт на возврат».

Рабочая модель: new/open/resolved/regressed. Определить взаимосвязь фильтров «Открытые», «Новые», «Возвращаются» и счётчиков. Политику позднего события после решения согласовать до реализации: исторический rebuild и повторное чтение checkpoint не должны автоматически создавать возврат. История переживает рестарт и не восстанавливается лишь из текущего окна логов.

«Поиск первопричины» в первом варианте открывает trace/context и связанные ошибки для расследования. Автоматический анализ причины и привязка к деплоям — отдельный функционал, данные которого пока отсутствуют. Waterfall в примере доступен после этапа 8; сначала показываются связанные логи.

Проверка: resolve сохраняется после рестарта, действительно новый случай меняет статус по принятой политике, read-only открытие не меняет статус, server count — distinct, автор/время действий видны, несвязанные stack/fingerprint не объединяются.

### 6. Инфраструктура и управление подключениями

Этот поток можно начать после этапа 1 независимо от паттернов.

6A: дать список зарегистрированных relay/агентов и переход в `/access`; проксировать health/имеющиеся core metrics в типизированный ответ dock, добавить собственные build/version/SSE/session показатели. Статус зарегистрированного узла до телеметрии — «Нет данных». Core visibility lag подписать как lag публикации, а не p95 доставки событий.

6B: согласовать узловую идентичность, получаемую из аутентифицированного контекста, и agent → relay → core heartbeat. Сейчас relay получает только множество хешей agent-токенов; нужен внутренний способ привязки к agent id. Произвольные source-поля не считать доказательством принадлежности узлу. Новые сообщения совместить с текущим бинарным контрактом и обновлением registry cache; персональные токены остаются прежней основой авторизации.

Телеметрия: heartbeat received_at, последнее событие/публикация, версия, spool used/limit, dropped, delivery failures и rate; distinct agent/relay identity. Определить heartbeat interval, TTL, degraded thresholds, freshness и состояние unknown после истечения данных. «Нет новых логов» отличается от offline: heartbeat есть, событий нет. Молчание приложения само по себе не означает сбой доставки.

6C: добавить core storage stats: Parquet/index/WAL bytes, свободное место, фактический retention и oldest segment. Прогноз заполнения возможен только при накопленной истории измерений и должен учитывать retention. P95 задержки event → core требует доступного core_received_at, согласованных часов и фильтрации недопустимых значений. Не вычислять его из agent ingested_at.

Проверка: heartbeat без логов, offline по TTL, telemetry stale, spool threshold, restart, отозванный токен и недоступный core дают правильные разные состояния; связь узла с событиями подтверждена авторизацией, storage соответствует диску. `/access` сохраняет выдачу токена один раз и запрет удаления relay с агентами.

### 7. Алерты: редактор, вычисление и доставка

7A после 3A/3B: rules CRUD, enabled, копирование, count threshold и отсутствие событий; редактор предложения валидирует те же типизированные filters/time windows. Хранить rule/channel/history/state в dock SQLite. Фоновый evaluator работает без открытого браузера и сохраняет состояние/checkpoint. Недоступные данные дают отдельное состояние ошибки, не «восстановлено» и не «сервис молчит».

Ввести переходы inactive → firing → recovered, cooldown, quiet hours с явной IANA timezone и одной утренней сводкой. История срабатываний содержит окно, значение, причину, ссылки на данные и delivery status. Сохранение правила не запускает произвольные команды.

Telegram и Discord — согласованные первые каналы. В редакторе заменить предвыбранный Slack из примера на Discord и добавить настройку его получателя. Секреты задаются серверу, API возвращает только безопасные метаданные каналов. Реальная конфигурация получателей потребуется при реализации. Сетевой worker использует ограниченные retries, учитывает rate limit и хранит очередь отправки на диске. Состояние правила, cooldown и outbox переживают рестарт; гарантии повторной доставки и idempotency явно определены.

7B после 4/5/6: new pattern за 30 дн, рост паттерна, возврат проблемы, молчание узла/сервиса с телеметрией, WARN относительно median истории. Различать окно событий и окно поступления, заполненность baseline и поздние данные; при нехватке retention не заявлять полную 30-дневную историю.

Добавить preview/backtest на истории тем же evaluator: количество firing-переходов, cooldown, quiet hours и recovery должны соответствовать реальному выполнению. Пока нет полного backtest, не показывать «за 7 дней сработало бы 3 раза». Slack/Email/Webhook относятся к последующим расширениям, с собственными настройками/проверками доставки.

Проверка: правило срабатывает и восстанавливается на контролируемой истории без браузера; cooldown/quiet hours/timezone работают; рестарт не теряет правило/очередь; retry не создаёт бесконечные повторы; сетевые ошибки не маскируются; baseline неполный → явный статус. Проверять доставку на тестовом получателе, production-получатели подключать отдельно при реализации.

### 8. Полноценные spans отдельным этапом

Отдельного trace-макета нет. До реализации уточнить контракт: span start/end/duration/status, parent relationship, service identity, несколько логов на span, пропущенные родители и рассинхронизация часов. Текущие `trace_id/span_id/parent_span_id` задают корреляцию, но не границы и длительность span.

Добавить поддержку необходимых данных в agent/relay/core, trace API и waterfall. После этого подключить durations в деталях проблемы. Не выдавать разность timestamp соседних логов за длительность операции.

Проверка: известное дерево spans и длительности совпадают с отправленными данными; отсутствие родителя/границы и неполный trace обозначены; логи доступны независимо от качества span-данных.

## Зависимости и порядок выпуска

```text
0 → 1 → 2 → 3A                   первый полезный выпуск
             └→ 3B               полная аналитика и поиск с точными summary
                 └→ 4 → 5        паттерны и проблемы
    1 → 6A → 6B → 6C             параллельный поток инфраструктуры
        3A/3B → 7A               простые рабочие алерты
        4 + 5 + 6 → 7B           полный набор правил из шаблона
    2 → 8                        полноценный trace отдельным этапом
```

Подключать cross-page действия только после готовности адресата: pattern → issue/alert, issue → alert, chart → logs, infra node → logs. Незавершённые функции не сопровождаются фальшивыми числами; до этапа можно скрыть действие или показать причину недоступности.

## Структура реализации и проверки

Фронтенд: `App.tsx`, `index.css`, `api.ts`, `pages/Logs.tsx`, новые `Analytics.tsx`, `Errors.tsx`, `Infrastructure.tsx`, `Alerts.tsx`; повторяемые UI в `components/`, общие модели событий/запросов — в `types/`. Внутри Logs сначала выделить управление запросом и потоком; не строить универсальный dashboard framework.

Dock: `api.rs`, `core_client.rs`, `live.rs` и узкие новые модули по функциональности; миграции `store.rs` для пользовательского состояния/правил/outbox. Core: `query.rs`, `analytics.rs`, `model.rs`, `columns.rs`, `index.rs`, позднее производные pattern/fingerprint данные и публикационный cursor. Agent/relay меняются только на этапе telemetry/span-контрактов.

Все новые browser API требуют AuthUser; изменения сохраняют Origin-проверку. Query/admin/notification secrets остаются на сервере. Ошибки query 400/410/429/503 и timeout переводятся по типизированному контракту; нельзя копировать admin error mapping с превращением всех отказов в core_unavailable. Новый timeout/cancellation согласуется с core до запуска аналитики.

Проверки на каждом этапе: значимые Rust integration tests для нового контракта/ошибок/миграций; UI-сценарии для поиска, cursor, ссылок, форм и переходов; визуальная сверка с эталонами на детерминированных fixtures. Web CI настроен на TypeScript/Vite build, Node unit-тесты и Playwright Chromium; браузерные тесты используют поддельные ответы API. Настоящий proxy проверяется Rust-тестами; первый выпуск дополнительно проверен браузером с настоящим dock и тестовым core. Нагрузочная и production-приёмка остаются отдельной проверкой.

Команды существующих проверок:

```sh
cargo test --locked --manifest-path Lognara-dock/Cargo.toml
cargo fmt --manifest-path Lognara-dock/Cargo.toml --check
cargo clippy --locked --manifest-path Lognara-dock/Cargo.toml --all-targets -- -D warnings
cd Lognara-dock/web
npm ci
npm run build
npm test
npx playwright install chromium
npm run test:e2e
```

Для этапов изменения core/agent/relay повторять проверки соответствующих crates и сквозного стенда. В каждом завершённом этапе обновлять относящиеся заметки Obsidian и делать самостоятельный короткий русский коммит по AGENTS.md; push не входит в этот план.

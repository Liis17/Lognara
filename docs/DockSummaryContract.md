# Dock: согласованная сводка (этап 3B)

База реализации: `5c219a9`. Контракт `POST /v1/stats/summary` в core и `POST /api/stats/summary` в dock. Query-токен core, сессия и Origin в dock; прежние endpoints сохраняются.

Запрос: `from`, `to`, `filters` (по умолчанию `{}`), необязательный `text` с той же all/phrase семантикой и валидацией, что у поиска; `interval_seconds` (60 по умолчанию, 1..86400, максимум 10000 корзин); необязательный `search_limit` (1..1000). Неизвестные поля отклоняются.

Ответ:

```ts
interface SummaryResponse {
  as_of: string;
  total: number;
  buckets: { timestamp: string; count: number; levels: Record<string, number> }[];
  levels: Record<string, number>; // все семь lowercase-уровней, включая нули
  error_services: { service: string | null; count: number }[]; // до 5, только ERROR
  duration: Duration;
  actions: { action: string | null; count: number; duration: Duration }[]; // до 20
  page: SearchResponse | null;
}
interface Duration {
  p95_ms: number | null;
  measured: number;
  coverage: number; // measured / число событий области, 0 для пустой области
  method: "tdigest";
}
```

Все блоки и первая страница (если запрошен `search_limit`) используют один удерживаемый Snapshot и watermark. Страница DESC, её курсор продолжает этот watermark. Сводка остаётся прежней при догрузке страниц; обновление выполняется новым запросом целиком. Trace сохраняет отдельный ASC API; данная сводка не заменяет Trace.

Текст подготавливается общим с поиском модулем: один tokenizer Tantivy, одинаковые ограничения и all/phrase. Для аналитики допускается последовательная проверка сообщения тем же подготовленным условием; отдельного синтаксиса и regex нет. Учитываются только timestamp в `[from,to)` и sequence <= watermark. Корзины выровнены по UTC, пустые заполнены нулями; сумма корзин и уровней равна total.

Duration читает существующий JSON-атрибут `duration_ms`; принимаются только конечные неотрицательные JSON-числа, включая 0. Строки, bool, null, отсутствие, отрицательные значения не измерены. p95 приблизительный t-digest DataFusion; измерений нет => null. До вычисления используется общий линейный масштаб для экстремальных duration, чтобы суммы центроидов не переполнялись; результат возвращается в миллисекундах. Покрытие и метод видны в UI. Миграция сырых сегментов не нужна. Таблица action считает события, не вызовы. Группы сортируются count DESC, затем ключ ASC (null после строк); лимит обозначен в UI.

Один summary занимает один из двух analytics slots. Агрегаты выполняются последовательно в общем ограниченном memory pool DataFusion; полный набор событий не собирается в память. Не кешировать весь отфильтрованный DataFrame. Blocking-поиск первой страницы удерживает permit до завершения даже при HTTP timeout. Старые query ошибки и deadline сохраняются, внешнего SQL нет.

UI: события используют summary с search_limit=50 для первой страницы, включая текстовые запросы; больше нет независимого histogram в режиме events. Шаг ограничен 86400 секундами. Если диапазон требует более 10000 UTC-корзин, Events сохраняет обычный поиск/cursor с явным объяснением отсутствия сводки; total/график не подменяются загруженными строками. Analytics использует одну summary на окно, прошлое окно запрашивается последовательно отдельной summary. Список сервисов остаётся отдельным ограниченным каталогом group-by. График показывает stacked count по семи уровням, p95/покрытие и таблица action подключены к серверу. KPI паттернов, полный экспорт и этапы 4–8 сюда не входят.

Проверки: равенство текстовых результатов поиску (all/phrase/Unicode/повторные токены), Parquet+Arrow и рестарт, границы времени/нули/семь уровней, согласованность page/count/cursor при новых публикациях, известная duration-выборка/невалидные значения/пустое окно, лимиты/ошибки/авторизация и Origin; UI text summary, stacked chart, p95/action и отмена устаревших ответов.
